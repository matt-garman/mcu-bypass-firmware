
= Electric Guitar Effect Engage/Bypass Scheme Firmware for Microcontrollers


== Why AVR Classic (ATtiny13a, ATtiny45, ATtiny85):

    * Readily available in SMD and through-hole
    * Low cost
    * avr tools - mature, cross-platform, fully-featured free/open-source tooling
    * simavr - open-source hardware simulation
    * Low-ish power by use of CPU IDLE mode for typically <1mA current draw
    * Trivial hardware implementation
    * Schmitt trigger GPIO pins

Note this project also supports the Microchip PIC10F322, which has _some_ of
the same benefits as AVR Classic, but the tooling is decidedly less compelling.
Compilation requires Microchip's XC8 compiler, which is not open source,
although Microchip does offer a limited free version of this compiler.  The
free tier XC8 restricts the options that are available.


== Why ATtiny202 (AVR-XT):

The ATtiny202 is a tinyAVR 0-series part: same vendor as AVR Classic, but a
different core generation (`avrxmega3`) with an entirely different peripheral
set.  It is the modern-silicon member of the supported set.

    * Still built by the same free/open avr-gcc + avr-libc toolchain, so the
      open-tooling property that motivates AVR Classic is preserved
    * Current production part rather than a mature/legacy one, with a
      correspondingly long expected availability horizon
    * 2 KB flash and 128 bytes SRAM: roughly double the ATtiny13a's flash and
      SRAM, so the firmware sits at ~40% of flash instead of ~70%
    * An **AEC-Q100 automotive-qualified** variant of this family exists
      (125 °C), which is a meaningfully stronger environmental rating than any
      other supported part carries
    * A genuinely fuse-locked watchdog: once `WDTCFG` is programmed, the WDT
      cannot be disabled by software at all (see Failsafe Mechanisms), which is
      a stronger guarantee than the classic parts' WDTON fuse
    * Programmed over UPDI, a single-wire interface that does not consume the
      RESET pin the way debugWIRE does

The trade-offs are honest ones and are recorded where they bite:

    * **Packaging.** The ATtiny202 is SOIC-8 / UDFN-8 only — there is no
      through-hole DIP version.  For hand-built one-offs the ATtiny13a or
      PIC10F322 remain the friendlier choice.
    * **Device pack.** Building for it needs Microchip's ATtiny_DFP device
      files, which the packaged avr-gcc 7.3.0 does not carry.  That is a
      Microchip download (no account or EULA), fetched on demand and version
      pinned; see TOOLCHAIN.adoc.  A modern from-source avr-libc (>= 2.2.0) has
      native ATtiny202 support and would remove this dependency.
    * **Simulation.** Neither simavr nor QEMU models the AVR8X core.  The
      dynamic harness runs on yasimavr instead, which is a genuine behavioural
      simulator but is not cycle-accurate; see "Known simulator gaps" in
      test/README.md for exactly what that does and does not cover.


== High-Level Functional Description

The microcontroller will be used with a physical human-operated
footswitch (momentary, normally open), and a circuit-switching
mechanism (an electric analog switch, CD4053/TMUX4053, or a two-coil
latching mechanical relay).  These components comprise a sub-circuit
of a larger effect circuit, typically for use in a pedal.

The user uses the footswitch to toggle between two states, "engaged"
and "bypass".  In the "engaged" state, the audio signal is routed
through some kind of effect; in "bypass", the effect is routed
straight through (as though the user removed the device entirely
from the signal chain).

This switching sub-circuit also has a status indicator LED; when the
effect is "engaged", the status LED should be lit, and when the
effect is in "bypass", the status LED should be dark.

Therefore, the MCU needs to:
    * maintain state (engage/bypass)
    * light or dark the status LED
    * respond to footswitch presses (including debounce)
    * control the actual signal switching mechanism (4053/relay)

At power-on, the circuit should default to the bypass state with the
LED dark (no state persistence between power cycles).

The state change should feel immediate to the user, and be triggered
on press (not on release).

This sub-circuit should be as robust as possible and assume likely
adverse conditions:
    * high temperature (e.g. noon-time Death Valley performance)
    * EMI/RFI (e.g. cell phones, wifi, fluorescent lighting, AC
      motors, proximity to radio station, etc)

== Reliability Goals
    * Reference-quality
    * World-class touring musician grade
    * Suitable for use by established market-leading manufacturers
      (e.g. Boss, Ibanez)
    * Under assumed operating conditions, one physical press must
      generate exactly one state change
    * One physical release must generate zero state changes
    * Resiliency against EMI/RFI-induced false state changes in
      expected operating environments
    * Switch bounce must never generate multiple state changes
    * Holding the switch down for several seconds must not generate
      additional state changes
    * Fast, repeated taps should always be recognized (see Caveats
      and Limitations)
    * Latency should feel instantaneous as possible given switch
      age/quality and environmental noise: <10ms under ideal
      circumstances
    * Behavior must be deterministic and analyzable


== Caveats and Limitations
    * The footswitch polling loop is based on a 1ms timer, driven by
      the AVR's builtin oscillator; this oscillator can drift
      +/- 10% (e.g. voltage fluctuations, temperature), which means
      actual sampling is roughly 0.9-1.1ms.  The algorithm still
      holds, and timing variations of this magnitude will not be
      perceptible to the user and are therefore acceptable.
    * Pop/click suppression is provided by the "4053 with muting"
      variant; the other two schemes (simple 4053, relay) do not
      have explicit pop/click suppression
    * The design could arguably be made more battery-friendly by use
      of a DEEP_SLEEP state when waiting for a footswitch press;
      that may be considered for a future revision - but the current
      design bias is towards simplicity and verifiability
    * By design, no recovery is currently provided for a
      mechanically stuck switch
    * "Fast repeated taps": under ideal conditions, the pure debounce model
      and ISR-driven AVR shells can re-arm 33ms after a press begins. The
      polled PIC10F322 simple/mute/relay variants use conservative nominal
      press-onset budgets of 33ms/38ms/45ms respectively because mute and
      relay actuation block sampling for 5ms/12ms after the toggle. The latched
      timer flag normally preserves one pending sample after a block, so an
      ideal simulated mute/relay path can re-arm roughly one tick sooner
      (about 37ms/44ms); instruction overhead and sample phase make the exact
      physical minimum non-integral. Noise and old switches lengthen recognition,
      while oscillator tolerance can move nominal wall time in either direction.
    * On the PIC10F322 port specifically: the footswitch loop is
      polled (Model B, no timer interrupt), so while a blocking
      output actuation runs - the relay coil pulse (12ms) or the
      CD4053 mute (5ms), a busy delay inside the state change -
      the loop pauses and the footswitch is not sampled.  The
      debounce integrator counts loop ticks. A press still toggles after
      PRESSED_THRESH sampled low ticks; the block starts only after that
      toggle, with the lockout counter already loaded. If the user releases
      immediately, those first 5ms/12ms of physical release occur while the
      mute/relay routine is still blocking and cannot drain the counter. The
      conservative release hold budget is therefore block + RELEASE_THRESH
      wall-time milliseconds before re-arm. TMR2 continues during the block and
      its latched flag normally supplies one immediate post-block sample, so the
      ideal earliest path can be about one tick shorter; the full-block budget
      remains robust to instruction overhead and sample phase. From one press
      onset to the next, use PRESSED_THRESH + block + RELEASE_THRESH for
      qualification: 33ms simple, 38ms mute, and 45ms relay. A normal physical
      tap clears these budgets comfortably. AVR Classic is unaffected because
      its timer ISR keeps integrating through the blocking pulse. The driver
      compile-time assertions bound block < RELEASE_THRESH, which keeps the
      conservative PIC release/re-arm wall-time budget below
      2 * RELEASE_THRESH; they do not make the block disappear from that budget.
    * The design attempts to be EMI/RFI resilient; however, an
      old/low-quality/fouled-contact footswitch might be very
      "bouncy"; the design can't distinguish EMI/RFI noise from
      switch bounce.  The tradeoff is that increased noise/bounce
      immunity reduces responsiveness.  Therefore, the firmware
      design assumes the following:
        ** High quality, modern footswitch
        ** Short (<10cm) leads between footswitch and PCB
        ** Footswitch leads are tightly twisted
        ** PCB and footswitch wiring housed in a grounded metal
           enclosure


== Failsafe Mechanisms

The firmware takes advantage of two microcontroller features in
order to fail gracefully in the face of extraordinary circumstances:

    * Brownout detection (BOD), essentially low voltage detection.
      The hardware design assumes an LP2950 or AP7375 regulator to
      provide 5v to the MCU from the parent circuit's 9-18v supply.
      AVR Classic MCUs provide various BOD levels via
      programmed fuses: 4.3v, 2.7v, 1.8v.  This firmware is
      configured with a 4.3v BOD fuse.  Thus, the design will
      trigger a reset - forced bypass state - if the voltage drops
      below this level.  While the MCU itself can run at lower
      voltages, connected peripherals cannot, particularly a 5v
      relay coil.  The assumption is that the parent effect is
      designed for 9-18v operation, so is almost certainly
      performing out-of-spec at a voltage below 5v.
+
NOTE: The 4.3v figure above is the *AVR Classic* (ATtiny13a/45/85)
BOD fuse. The BOD/BOR floor is MCU-family-specific and not every
supported part can enforce the >4v peripheral-safe threshold:
+
[horizontal]
AVR Classic (ATtiny13a/45/85):: 4.3v BOD fuse -- enforces the >4v
  floor the 5v relay coil / MOSFET peripherals require.
ATtiny202 (AVR-XT):: BODCFG fuse `LVL=BODLEVEL7` (~4.2v), with BOD
  enabled in both active and sleep modes. This is the AVR-XT
  analogue of the classic 4.3v BOD and likewise enforces the >4v
  peripheral-safe floor.
PIC10F322:: BOR is enabled at the highest available trip
  (`BORV=HI`), but the PIC10F322's trip points are only ~2.4v (LO) /
  ~2.7v (HI). The PIC therefore *cannot* enforce a >4v floor in
  firmware -- this is a hardware-design limitation. A build on
  either PIC part that drives >4v peripherals must guarantee the
  peripheral-safe supply in hardware (e.g. regulator dropout /
  supervisor), not rely on the MCU's BOR.
PIC10F320:: same silicon family and the same BOR configuration as
  the PIC10F322 (`BOREN=ON`, `LPBOR=OFF`, `BORV=HI`), so the same
  ~2.4v (LO) / ~2.7v (HI) trip points and *exactly the same caveat*
  apply.

    * Watchdog timeout (WDT): while the program flow has been
      exhaustively tested/simulated, including formal
      state-analysis, there is the possibility of extreme
      environmental factors that could corrupt the runtime state:
      cosmic rays, extreme EMI/RFI.  Besides explicit runtime sanity
      checks, the firmware also employs the MCU's WDT functionality:
      crucial parts of the firmware must regularly "pet the
      watchdog" (i.e., reset the timeout); if an extreme-outlier
      situation causes the WDT to timeout, it will force the
      firmware to reset (force to bypass).  Note that the WDT reset
      triggers only under highly improbable, "should be impossible"
      circumstances that are beyond the control of the firmware.


== Asymmetric Debounce Timing

The design deliberately uses asymmetric timing for debouncing the
switch press and release.  The goal is to use a shorter time window
for press-debounce, so the state change feels instantaneous to the
user.  The release-debounce, or lock-out period, is longer so as to
"hide" additional debounce latency from the user.

    * PRESSED_THRESH upper bound (latency constraint):
      At worst-case clock (+10% RC drift), one tick = 1.111ms. For
      <10ms press latency: PRESSED_THRESH = floor(10 / 1.111) = 9.
      Current value 8 has a 1-tick margin.  Note that changing to 10
      10 would violate the "<10ms press latency" goal.  Also note
      that a highly bouncy switch, or significant EMI/RFI _will_
      cause the press latency to exceed 10ms.

    * PRESSED_THRESH lower bound (EMI rejection):
      The RC filter (1k series + 22nF to ground + approx. 7.5k pullup
      effective) has a time constant 22nF × (1k || 7.5k) =
      approx. 18µs. EMI spikes shorter than a few RC time constants are
      attenuated below the Schmitt threshold. The filter provides
      hardware-level rejection of spikes shorter than roughly 100µs. The
      1ms timer tick plus PRESSED_THRESH=8 means a spurious low must
      persist for 8ms (contiguous or accumulating) to register
      roughly 80× the hardware filter's corner.

    * RELEASE_THRESH (minimum lockout before next press):
      At the pure-algorithm sample level, and on ISR-driven AVR shells, the
      minimum press-onset interval is PRESSED_THRESH + RELEASE_THRESH = 33ms
      at nominal clock. For the polled PIC shell, conservative qualification
      adds the full blocking output actuation after the toggle: 33ms simple,
      38ms mute, 45ms relay. A pending TMR2 flag can make the ideal mute/relay
      path roughly one tick shorter, so these are robust budgets rather than
      claims of exact physical minima.

      AVR Classic; deliberately not used in this design

== ATtiny202 SOIC-8 Package Pinout

The ATtiny202 is **not available in a through-hole DIP package** — SOIC-8 and
UDFN-8 only. Of its eight pins, six are I/O: PA4 and PA5 exist in the die's
PORTA register but are not bonded out on the 8-pin package.

Physical pin numbering below is taken from the `SOIC8` pinout in Microchip's own
`ATtiny202.atdf` device file, as shipped in the pinned ATtiny_DFP the build uses
(see `TOOLCHAIN.adoc`) — not from a redrawn diagram. The vendored four-file DFP
subset does not include the `.atdf`, so re-checking this means reading it out of
the full atpack.

....
                                        +----+
                               VDD pin1-|    |-pin8 GND
               (AIN6/spare)    PA6 pin2-|    |-pin7 PA3 (AIN3/EXTCLK/CTL2/relay SET)
       (AIN7/footswitch input) PA7 pin3-|    |-pin6 PA0 (UPDI/~RESET)
             (AIN1/status LED) PA1 pin4-|    |-pin5 PA2 (AIN2/CTL1/relay RESET)
                                        +----+
....

Pin roles in this design map one-for-one onto the AVR Classic assignment above:

    * PA7: input; footswitch, internal pull-up, normally high, pulled low when
      pressed (the classic shell's PB0)
    * PA1: output; status LED, high when engaged (PB1)
    * PA2: output; x4053 control / relay RESET coil (PB2)
    * PA3: output; x4053 second control / relay SET coil (PB3)
    * PA6: output driven low.  It is otherwise unused; driving it low rather
      than leaving it an input keeps it from floating, and it is included in the
      exact-direction and output-latch integrity checks (see Failsafe
      Mechanisms) so a corrupted PORTA is still detected on that bit.
    * PA0: left as UPDI (the `RSTPINCFG` field of `SYSCFG0` keeps it as the
      programming pin).  It is never used as GPIO, which is why the design fits
      an 8-pin part without sacrificing the programming interface.

`src/bypass_pins_avr_xt.h` is the single source of truth for these assignments;
`bypass_mcu_avr_xt.c` pins each of them to `<avr/io.h>`'s generic `PINn_bp`
constants with compile-time asserts, so a typo in the map cannot misroute a pin.

NOTE: unlike the classic AVR parts, PA7 here is deliberately placed well clear
of the UPDI pin.  Putting the footswitch on PA0 would have shared it with the
programming interface.


== Optimal Footswitch-GPIO Wiring for EMI/RFI resiliency

The GPIO pin tied to the footswitch (normally high) will have some
hardware-level EMI/RFI protections and also aid with debounce.
Wiring is as follows:

Footswitch lead 1: GND

Footswitch lead 2 ("FOOTSW_PIN"):

    * TVS diode to ground (cathode=signal, anode=GND)
    * series ferrite bead
    * series 1k resistor ("a" side to FB, "b" side to "node b")
    * 22nF capacitor "node b" to ground (close to MCU GPIO pin)
    * 10k pullup resistor "node b" to VCC

Wiring diagram:
....
                                       VCC(5v)
                                          |
                                        [10k]
                                          |
  FOOTSW_PIN -----+-----[FB]-----[1k]-----+-----GPIO_PIN
                  |                       |
               [TVS-K]                 [22nF]
               [TVS-A]                    |
                  |                       |
                 GND                     GND
....

Note this wiring is overbuilt for the intended purpose.  All parts
are recommended for best EMI/RFI resiliency, but for non-adverse
environmental conditions and/or prioritizing reduced BOM cost and
PCB space, the TVS diode and ferrite bead can be omitted.


== CD4053 Notes

    * the newer TMUX4053 switches can be controlled with logic
      levels lower than the voltage supply (e.g. CMOS, TTL)
    * the older CD4053 needs logic "true" to be the same level as
      the voltage supply
    * the AVR Classic MCU will run at 5v, but the 4053 will run at
      the effect voltage (9 to 18 volts)
    * 5v rail derived via LP2950 for through-hole implementation
      or AP7375 for SMD implementation
    * 5v rail only for MCU and footswitch - everything else
      (including status LED) is powered from the parent 9-18v rail
    * therefore, the 4053 control pins will be held to effect
      voltage via pullup resistor; the control pins will be pulled
      low (to ground) via a mosfet; that mosfet's gate will be
      controlled by AVR PB2
    * therefore, the PB2 pin value is actually inverted at the
      CD4053:
        ** PB2 high -> mosfet on -> 4053 control pins low
        ** PB2 low -> mosfet off -> 4053 control pins high
    * the 4053 is wired such that:
        ** control pins high = bypass
        ** control pins low = engaged
    * assume 2n7000/2n7002 mosfets for CD4053 control and LED
      control

=== Circuit Net Naming Conventions

    * JOU = output jack, i.e. final output signal to next device/amp
    * INP = input signal
    * FXO = effect output/return
    * FXN = effect input/send

=== CD4053 vs TMUX4053 Notes

    * CD4053 available in through-hole and surface-mount
    * TMUX4053 surface-mount only
    * TMUX4053 can use lower-voltage logic true (e.g. CMOS, TTL)
    * CD4053 needs logic true to be at VDD
    * VDD will be effect voltage (typically 9-18v)
    * Two board options, one firmware image:
        ** CD4053 (control logic at VDD, typically 9-18v): the 5v MCU
           cannot drive the control pins directly, so each control pin is
           held HIGH via a pullup to VDD and pulled LOW through a MOSFET
           whose gate the MCU drives. This inverts the MCU signal:
           MCU high -> switch control low; MCU low -> switch control high.
        ** TMUX4053 (logic-level control, e.g. CMOS/TTL): the MCU drives
           the control pins DIRECTLY. Each control pin has a pulldown to
           GND, so MCU low -> switch control low; MCU high -> switch
           control high. There is no MOSFET.
    * Fail-safe by design: the natural state, with the MCU pins undriven
      (they sit at their pulldown level, i.e. low), must be BYPASS. For the
      CD4053 the MOSFET is then off and the control pins sit HIGH; for the
      TMUX they sit LOW. The TMUX board therefore SWAPS its analog throws
      (A0/A1, B0/B1, C0/C1) relative to the CD4053 so that both parts land
      in BYPASS from their opposite rest levels (see the per-part truth
      tables below).
    * Consequence: the CD4053's MOSFET inversion and the TMUX's swapped
      throws cancel, so the MCU drives an IDENTICAL polarity for both parts
      (BYPASS = pin low, ENGAGE = pin high). A single firmware image
      (cd4053 / mute) drives BOTH boards -- there is deliberately no
      separate TMUX build. (An earlier revision shipped separate _tmux
      images that re-inverted the MCU drive; because the hardware already
      cancels the difference, that was a latent polarity bug and the
      variants were byte-identical once corrected, so they were dropped.)

== Resource Utilization

The firmware is deliberately tiny, leaving large headroom on every supported
part. Measured figures per MCU family follow.

=== AVR Classic family

Flash figures below are reported by `avr-size`; static data comprises
two global variables, `timer_isr_called_` (1 byte, shared between main and
the timer ISR) and `ctx_` (3-byte `debounce_context_t` struct containing
`program_state`, `effect_state`, and `debounce_counter`), totalling 4 bytes;
and peak stack is the empirical high-water mark measured by the simavr
stack-canary test (see Testing and Validation above).

|===

| ATtiny13a | relay   | 756 bytes           | 73.8% of 1 KB
| ATtiny13a | mute    | 756 bytes           | 73.8% of 1 KB
| ATtiny45  | cd4053  | 742 bytes           | 18.1% of 4 KB

SRAM use is dominated by 4 bytes of static data; peak stack measured 31 bytes

The PIC10F322 port has a much tighter device budget, 512 fourteen-bit program

== PIC Power / Current Draw

Applies to both PIC parts: they share a datasheet family, a clock choice and a
main-loop model.

The PIC core runs at **2 MHz** (HFINTOSC) on a **polled 1 ms tick** — a busy-wait
on `TMR2IF`, never asleep. This is the opposite of the AVR Classic design, which
sleeps between ISR-driven samples, and it is deliberate. The PIC10F320/322 has no
idle mode, and its only Sleep-capable periodic wake is the coarse WDT (TMR0/TMR2
are FOSC/4-clocked and stop in Sleep), so a *precise* 1 ms tick necessarily means
staying awake. The design spends that power to buy a precise tick and a
high-margin, independent watchdog; a deep-sleep scheme would have to give up one
or both.

Because the loop is always awake, the clock frequency sets the current draw. The
core is clocked at 2 MHz rather than the part's 16 MHz maximum: the debounce plus
per-tick sanity work is only ~210 instruction cycles, so 2 MHz (500 cycles/ms)
runs it at ~42% utilisation — comfortable headroom — while roughly *halving* the
supply current.

|===
| FOSC | active IDD @ 5 V (typ) | ~ power | per-tick headroom

| 16 MHz   | ~0.85 mA | ~4.25 mW | 19x
| *2 MHz*  | *~0.43 mA* | *~2.1 mW* | *2.4x*
|===

(IDD interpolated from DS40001585 D017–D019; the 16 MHz row is the tabulated
figure.) A lower clock also emits less high-frequency switching noise into the
analog audio path.

This firmware is **not** battery-optimised, and the table should not be read as
if it were: in a typical pedal the always-on status LED and the analog signal
path dominate the supply, so the MCU's sub-milliamp draw is usually negligible.
The 2 MHz choice is simply "no reason to burn 4 mW when 2 does the same job."


== Multi-MCU Architecture: Shared Core, Per-MCU Shell

The firmware targets three MCU core generations -- AVR Classic, AVR-XT and
PIC10F32x -- that share the debounce algorithm but differ completely at the
register level. The split that makes
this work has two rules.

**The algorithm is shared, exactly once.** `src/bypass_pure.c` is the
functional core: no hardware access, no globals, no side effects. Every
target compiles the same file, and it is the sole subject of the host tests
and the formal proofs. Nothing about it is per-MCU.

**The main loop is NOT shared.** Each MCU shell owns its own `main()`, tick
mechanism, and watchdog-liveness model; only the leaf hardware operations are
abstracted. This is a deliberate decision, revisited when the second and third
shells were written, and it is worth recording why — the alternative (one
portable `main()` parameterized by an interface) looks cleaner and is wrong
here.

The AVR Classic design samples the footswitch *inside* the 1 ms Timer0 ISR
while `main()` sleeps, and proves liveness through the `timer_isr_called_`
ISR-to-main handshake. The PIC10F322 uses a fundamentally different model: no
tick ISR at all, a single polled loop that waits on `TMR2IF`, samples, updates,
and pets the watchdog, where reaching `CLRWDT` *is* the liveness proof. A single
shared `main()` cannot express both without changing AVR's ISR-sampling
behaviour, which would invalidate the documented design and the tests built on
it — lock-step co-simulation, ISR-jitter, and the handshake mutants.

The ATtiny202 follows the AVR Classic model rather than the PIC one, but on
entirely different peripherals: the tick is TCB0 in periodic-interrupt mode
(`CCMP` = 1999 at 2 MHz) instead of Timer0 compare-match, the sleep is AVR-XT
IDLE via `SLPCTRL`, and the watchdog is fuse-locked by `WDTCFG` so `hw_wdt_pet()`
is a bare `wdr` with nothing to arm. Because it integrates in the ISR, it
inherits the classic lane's timing properties exactly — including the one that
matters most for actuation: the ISR keeps sampling through a blocking relay or
mute pulse, so no ticks are lost, which is why the AVR shells and the polled PIC
shell qualify press timing differently (see Asymmetric Debounce Timing). This is
the clearest illustration of why the shells are separate: the AVR-XT and AVR
Classic shells share a *model* and share none of their register code.

So `main()`, the tick source, `init()` as orchestrator, and the reset path stay
file-static inside each shell. The consequences are visible elsewhere in this
document: the polled PIC shell qualifies press timing differently than the
ISR-driven AVR shells (see Asymmetric Debounce Timing), and it carries no
`timer_isr_called_` byte (see Resource Utilization).

**What the shared interface does cover.** `src/bypass_hw_iface.h` is the
*output-driver* boundary only: the GPIO leaf operations a shell provides to a
driver (`hw_pin_set_*`, `hw_led_pin_set_*`, `hw_configure_output_pins`,
`hw_output_state_intact`) and the operations a driver provides back
(`hw_set_bypass_state`, `hw_set_engaged_state`, `hw_is_sanity_check_failed`,
`hw_init_output_pins`). The pin-direction API is mask-based so one driver body
serves all targets: the AVR Classic implementation writes `DDRB`, the AVR-XT
one writes `PORTA.DIR`, and the PIC maps the mask onto `TRISA`.

Everything else — footswitch read, watchdog arm and pet, clock and peripheral
bring-up, wait-for-tick, the forced-reset path, and the SFR integrity checks —
is shell-private and rewritten per shell. That is not an oversight: MISRA
Rule 8.7 flagged the earlier arrangement, since each of those helpers is
referenced only within its own translation unit. Adding a target normally means
adding a shell plus a pin map, and reusing the core and all three output
drivers unchanged. No existing shell needs to be refactored.

=== The one target that does not follow this rule

The PIC10F320 is the exception, and it is worth naming here rather than leaving
the paragraph above to be read as universal. It has **256 words of flash, half
the PIC10F322's**, and the shared-core-plus-shell arrangement does not fit —
measured, not assumed: the modular firmware overshoots by roughly 100 words
(`docs/pic10f320_feasibility.md`).

Its firmware, `src/bypass_mcu_pic10f320.c`, therefore reuses *neither* the core
nor the output drivers as linked code. It is a single self-contained file with
the integrator, the state machine, the power-on initialisation and the three
output stages hand-inlined into `main()` and `#if defined(OUTPUT_*)` blocks. The
source tree therefore has six release targets implemented by four
shells plus one inlined implementation; the PIC10F320's first unified release is
still pending qualification.

That trades the compile-the-verified-core property for a behavioural
equivalence argument against the same core — host equivalence tick-for-tick,
real-HEX lock-step in gpsim, host and target fault injection, and an exact-line
firmware coverage gate. It is integrated and wired into the release gates, but
is not present in a published unified release yet.
**`docs/pic10f320_special_case.md` is the single authoritative statement of what
that difference does and does not buy**; this section deliberately does not
restate the assurance argument.

== AVR Classic Program Flow

=== Functional Description

Define two program states: PRESS_DEBOUNCE_WAIT, RELEASE_DEBOUNCE_WAIT
Define two effect-circuit states: ENGAGED, BYPASS
Define constants (see "Asymmetric Debounce Timing" above for rationale)
    * RELEASE_THRESH = 25
    * PRESSED_THRESH = 8

The core mechanism is a saturating integrator: a counter that
increments by one per millisecond when the footswitch reads closed,
and decrements by one per millisecond when it reads open, bounded
between 0 and RELEASE_THRESH. A simple debounce timer resets on any
noise sample; the integrator tolerates noise, requiring only that
the majority of samples over a window indicate the intended state. A
spike shorter than PRESSED_THRESH milliseconds cannot reach the
threshold even if perfectly timed. A real press, even through
moderate contact bounce or EMI, accumulates reliably because each
clean low sample contributes persistently.

The state machine has two states. In PRESS_DEBOUNCE_WAIT, the
integrator climbs while the switch is held and falls while released.
When it reaches PRESSED_THRESH, the effect is toggled immediately
and the counter is loaded with RELEASE_THRESH, arming the lockout.
In RELEASE_DEBOUNCE_WAIT, the integrator can only drain (the switch
is being released). Only when it reaches zero does the machine
re-arm for the next press. This lockout prevents switch bounce on
release from generating a second event, and prevents a held switch
from re-triggering.

The thresholds are asymmetric by design. PRESSED_THRESH (8ms) is
kept low for fast response; it is the minimum sustained press
needed to register, and sets the best-case latency. RELEASE_THRESH
(25ms) is larger, providing robust lockout against release bounce
while still allowing fast repeated taps (minimum tap interval =
PRESSED_THRESH + RELEASE_THRESH = 33ms). See "Asymmetric Debounce
Timing" for details.

Additionally, the MCU's watchdog feature is used to reset the
device to the default state (bypass, status LED dark) in the event
of unexpected error, bit flip, etc.


=== State Machine

Saturating integrator (ISR, every 1ms, runs in both states):

  if footswitch pin low  (switch closed):  if counter < RELEASE_THRESH: counter++
  if footswitch pin high (switch open):    if counter > 0             : counter--



.Table Program state machine (main loop, evaluated after each ISR wake)
|===
| Current State        | Condition                   | Effect action                                    | Next State

| PRESS_DEBOUNCE_WAIT  | counter >= PRESSED_THRESH   | Toggle engaged/bypass; counter = RELEASE_THRESH  | RELEASE_DEBOUNCE_WAIT
| PRESS_DEBOUNCE_WAIT  | counter <  PRESSED_THRESH   | (none)                                           | PRESS_DEBOUNCE_WAIT
| RELEASE_DEBOUNCE_WAIT| counter == 0                | (none)                                           | PRESS_DEBOUNCE_WAIT
| RELEASE_DEBOUNCE_WAIT| counter >  0                | (none)                                           | RELEASE_DEBOUNCE_WAIT
|===
