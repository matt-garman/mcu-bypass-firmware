
= Electric Guitar Effect Engage/Bypass Scheme Firmware for Microcontrollers


[[why-avr-classic]]
== Why AVR Classic (ATtiny13a, ATtiny45, ATtiny85)

    * Readily available in SMD and through-hole
    * "Legacy" parts as an advantge: an extremely mature product that has been deployed in countless applications *and* is still in production and readily available
    * Low cost
    * avr tools - mature, cross-platform, fully-featured free/open-source tooling
    * simavr - open-source hardware simulation
    * Low-ish power by use of CPU IDLE mode for typically <1mA current draw
    * Trivial hardware implementation
    * Schmitt trigger GPIO pins


[[why-avr-xt]]
== Why ATtiny202 (AVR-XT)

The ATtiny202 is a tinyAVR 0-series part: same vendor as AVR Classic, but a
different core generation (`avrxmega3`) with an entirely different peripheral
set.  It is the modern-silicon member of the supported set.

    * Also supported by the open-source `avrtools` (avr-gcc + avr-libc toolchain)
    * Not a legacy legacy part, but still mature; we can expect a longer availability horizon compared to AVR Classic
    * Roughly double the flash and SRAM of the ATtiny13a
    * An **AEC-Q100 automotive-qualified** variant exists (125 °C)
    * A genuinely fuse-locked watchdog: the WDT cannot be disabled by software
      (a stronger guarantee than the classic parts' WDTON fuse)
    * Programmed over UPDI, a single-wire interface that does not consume the
      RESET pin the way debugWIRE does

Trade-offs versus AVR Classic:

    * Packaging: the ATtiny202 is surface-mount only (though SOIC-8 to DIP-8 adapters exist)
    * Vendor "Device Pack": avr-gcc v7.3.0 does not have Microchib's ATtiny_DFP
      device files, which are required for compilation; it's a free download
      that is fetched on demand and version pinned (see TOOLCHAIN.adoc).  Note
      that newer avr-libc (>= 2.2.0) has native ATtiny202 support.
    * Simulation: Neither simavr nor QEMU models the AVR8X core, but
      [yasimavr](https://github.com/clesav/yasimavr) exists.  See "Known gaps
      (AVR-XT - hardware-bench only)" in test/README.md for exactly what that
      does/does not cover.


== PIC Support

This project also supports the Microchip PIC10F322, PIC10F320 and PIC12F675
microcontrollers, which have _some_ of the same benefits as AVR Classic, but
the tooling is decidedly less compelling.  They use Microchip's XC8 compiler and
PIC10-12Fxxx_DFP device pack.  XC8 is not open source, although Microchip offers
a limited free version; that free tier restricts the options that are
available.  PIC10F320's 256-word flash also requires the self-contained
architecture described in <<pic10f320-architecture>>.  The PIC10F32x ("enhanced
mid-range") and PIC12F675 ("classic mid-range") parts have different harware
cores, so their hardware-specific implementations ("shell") differ. See
<<pic12f675-architecture>> for design considerations unique to the PIC12F675.



== High-Level Functional Description

The microcontroller will be used with a physical human-operated
footswitch (momentary, normally open), and a circuit-switching
mechanism (an electric analog switch, CD4053/TMUX4053, or a two-coil
latching mechanical relay).  These components comprise a sub-circuit
of a larger effect circuit, typically for use in an effect pedal.

The user uses the footswitch to toggle between two states, "engaged"
and "bypass".  In the "engaged" state, the audio signal is routed
through some kind of effect; in "bypass", the effect is routed
straight through (as though the user removed the device entirely
from the signal chain).

This switching sub-circuit also has a status indicator LED; when the
effect is "engaged", the status LED should be lit, and when the
effect is in "bypass", the status LED should be dark.

Therefore, the MCU needs to:
    * maintain state (engage/bypass)
    * light or dark the status LED
    * respond to footswitch presses (including debounce)
    * control the actual signal switching mechanism (4053/relay)

At power-on, the circuit should default to the bypass state with the
LED dark (no state persistence between power cycles).

The state change should feel immediate to the user, and be triggered
on press (not on release).

This sub-circuit should be as robust as possible and assume likely
adverse conditions:
    * high temperature (e.g. noon-time Death Valley performance)
    * EMI/RFI (e.g. cell phones, wifi, fluorescent lighting, AC
      motors, proximity to radio station, etc)

== Reliability Goals
    * Reference-quality
    * World-class touring musician grade
    * Suitable for use by established market-leading manufacturers
      (e.g. Boss, Ibanez)
    * Under assumed operating conditions, one physical press must
      generate exactly one state change
    * One physical release must generate zero state changes
    * Resiliency against EMI/RFI-induced false state changes in
      expected operating environments
    * Switch bounce must never generate multiple state changes
    * Holding the switch down for several seconds must not generate
      additional state changes
    * Fast, repeated taps should always be recognized (see Caveats
      and Limitations)
    * Latency should feel instantaneous as possible given switch
      age/quality and environmental noise: <10ms under ideal
      circumstances
    * Behavior must be deterministic and analyzable


== Caveats and Limitations
    * Every implementation except PIC12F675 uses a nominal 1ms timer-derived
      sample cadence; PIC12F675 uses 1.024ms.  The AVR implementations sample
      in timer ISRs, while the PIC implementations poll their timer flags.
      Under the conservative +/-10% frequency envelope, the 1ms targets span
      roughly 0.909-1.111ms per sample and PIC12F675 spans roughly
      0.931-1.138ms. The algorithm counts samples and still holds; the
      resulting wall-time variation is not perceptible to the user.
    * Pop/click suppression is provided by the "4053 with muting"
      variant; the other two schemes (simple 4053, relay) do not
      have explicit pop/click suppression
    * The design could arguably be made more battery-friendly by use
      of a DEEP_SLEEP state when waiting for a footswitch press;
      that may be considered for a future revision; the current
      design bias is towards simplicity and verifiability
    * By design, no recovery is currently provided for a
      mechanically stuck switch
    * "Fast repeated taps": the pure debounce model and ISR-driven AVR shells
      schedule a conservative budget of 33 sample updates for a clean press followed by
      immediate release (8 accepted low samples + 25 high samples). At a nominal
      1ms tick this is called a 33ms qualification budget, not an exact physical
      minimum: the first through last sample span one fewer interval, and the
      first sample's phase puts ideal press-onset-to-re-arm time at roughly
      32-33ms. The polled PIC10F32x implementations use conservative nominal
      simple/mute/relay budgets of 33ms/38ms/45ms. PIC12F675's corresponding
      1.024ms-tick budgets are about 33.8ms/38.8ms/45.8ms. Mute and relay
      actuation block sampling for 5ms/12ms after the toggle. A PIC10F32x
      `TMR2IF` latched during that block can make the next sample immediate;
      PIC12F675's latched `T0IF` supplies only the first of four required 256us
      rollover observations. These are conservative qualification budgets, not
      exact physical minima. Noise and old switches lengthen recognition, while
      oscillator tolerance moves wall time in either direction.
    * On the PIC parts, the footswitch loop is polled (Model B: a polled
      hardware timer tick with the watchdog kept as a pure fault watchdog,
      no timer interrupt; the decision and its alternatives are in
      <<pic-model-b>>), so while a blocking
      output actuation runs - the relay coil pulse (12ms) or the
      CD4053 mute (5ms), a busy delay inside the state change -
      the loop pauses and the footswitch is not sampled.  The
      debounce integrator counts loop ticks. A press still toggles after
      PRESSED_THRESH sampled low ticks; the block starts only after that
      toggle, with the lockout counter already loaded. If the user releases
      immediately, those first 5ms/12ms of physical release occur while the
      mute/relay routine is still blocking and cannot drain the counter. The
      conservative release hold budget is therefore block + RELEASE_THRESH
      nominal sample periods before re-arm. The hardware timer continues during
      the block. On PIC10F32x, a latched `TMR2IF` normally supplies one immediate
      post-block sample. On PIC12F675, a latched `T0IF` satisfies the first of the
      four rollover observations that form one sample, after which up to three
      more 256us rollovers remain. From one press onset to the next, use
      PRESSED_THRESH + block + RELEASE_THRESH as the conservative nominal
      qualification budget: 33ms/38ms/45ms for PIC10F32x and approximately
      33.8ms/38.8ms/45.8ms for PIC12F675. These are sample-count-derived budgets,
      not exact physical minima. A normal physical tap clears them comfortably.
      AVR Classic and AVR-XT are unaffected because their timer ISRs keep
      integrating through the blocking pulse. The driver
      compile-time assertions bound block < RELEASE_THRESH, which keeps the
      conservative PIC release/re-arm wall-time budget below
      2 * RELEASE_THRESH; they do not make the block disappear from that budget.
    * The design attempts to be EMI/RFI resilient; however, an
      old/low-quality/fouled-contact footswitch might be very
      "bouncy"; the design can't distinguish EMI/RFI noise from
      switch bounce.  The tradeoff is that increased noise/bounce
      immunity reduces responsiveness.  Therefore, the firmware
      design assumes the following:
        ** High quality, modern footswitch
        ** Short (<10cm) leads between footswitch and PCB
        ** Footswitch leads are tightly twisted
        ** PCB and footswitch wiring housed in a grounded metal
           enclosure


== Failsafe Mechanisms

The firmware fails gracefully in the face of extraordinary
circumstances by layering four mechanisms.  Two are microcontroller
features; the other two are firmware behaviours that detect a fault
and escalate it to a fail-safe recovery:

    * Brownout detection (BOD), essentially low voltage detection.
      The hardware design assumes an LP2950 or AP7375 regulator to
      provide 5v to the MCU from the parent circuit's 9-18v supply.
      AVR Classic MCUs provide various BOD levels via
      programmed fuses: 4.3v, 2.7v, 1.8v.  This firmware is
      configured with a 4.3v BOD fuse.  Thus, the design will
      trigger a reset - forced bypass state - if the voltage drops
      below this level.  While the MCU itself can run at lower
      voltages, connected peripherals cannot, particularly a 5v
      relay coil.  The assumption is that the parent effect is
      designed for 9-18v operation, so is almost certainly
      performing out-of-spec at a voltage below 5v.
+
NOTE: The 4.3v figure above is the *AVR Classic* (ATtiny13a/45/85)
BOD fuse. The BOD/BOR floor is MCU-family-specific and not every
supported part can enforce the >4v peripheral-safe threshold:
+
[horizontal]
AVR Classic (ATtiny13a/45/85):: 4.3v BOD fuse -- enforces the >4v
  floor the 5v relay coil / MOSFET peripherals require.
ATtiny202 (AVR-XT):: BODCFG fuse `LVL=BODLEVEL7` (~4.2v), with BOD
  enabled in both active and sleep modes. This is the AVR-XT
  analogue of the classic 4.3v BOD and likewise enforces the >4v
  peripheral-safe floor.
PIC10F322:: BOR is enabled at the highest available trip
  (`BORV=HI`), but the PIC10F322's trip points are only ~2.4v (LO) /
  ~2.7v (HI). The PIC therefore *cannot* enforce a >4v floor in
  firmware -- this is a hardware-design limitation. A build on
  either PIC10F32x part that drives >4v peripherals must guarantee the
  peripheral-safe supply in hardware (e.g. regulator dropout /
  supervisor), not rely on the MCU's BOR.
PIC10F320:: same silicon family and the same BOR configuration as
  the PIC10F322 (`BOREN=ON`, `LPBOR=OFF`, `BORV=HI`), so the same
  ~2.4v (LO) / ~2.7v (HI) trip points and *exactly the same caveat*
  apply.
PIC12F675:: BOD is enabled (`BOREN=ON`) at a fixed 2.025-2.175v trip
  range; this part has no `BORV` selection. It therefore cannot enforce the
  >4v peripheral-safe floor either. External supply supervision is required
  when the connected circuit must stop operating above the PIC12F675 BOD range.

    * Watchdog timeout (WDT): while the program flow has been
      exhaustively tested/simulated, including formal
      state-analysis, there is the possibility of extreme
      environmental factors that could corrupt the runtime state:
      cosmic rays, extreme EMI/RFI.  Besides explicit runtime sanity
      checks, the firmware also employs the MCU's WDT functionality:
      crucial parts of the firmware must regularly "pet the
      watchdog" (i.e., reset the timeout); if an extreme-outlier
      situation causes the WDT to timeout, it will force the
      firmware to reset (force to bypass).  Note that the WDT reset
      triggers only under highly improbable, "should be impossible"
      circumstances that are beyond the control of the firmware.
      The watchdog is also the deliberate escalation path for the
      integrity check described next: a corrupted context that the
      firmware detects but cannot correct is turned into a reset
      rather than being acted upon.

    * Runtime state-integrity checking: the two hardware mechanisms
      above catch a supply that has left spec and a program that has
      stopped making progress, but neither notices a corrupted
      *value* inside a program that is still running normally.
      Every serviced tick therefore snapshots and re-validates the debounce
      context before acting on it.  A range check rejects any of
      `program_state`, `effect_state` or `debounce_counter` that has
      left its legal domain.  That check exists only because the
      representation is wider than the domain, which is a priced
      decision rather than an accident.  Packing the three members
      into bitfields exactly as wide as their legal values was
      measured to save 47 program words, and was refused at every
      target rather than only where flash is tight: a one-bit
      `program_state` can never hold an out-of-range value, so the
      check becomes dead code; all three members would then share a
      single byte, so any one flip silently mutates live state with
      nothing able to represent -- and therefore detect -- the
      corruption; and the compile-time counter bound would fall from
      255 to 63, narrowing the thresholds this design is allowed to
      choose.  A flip that lands *inside* the legal
      range is caught by a checksum: the firmware keeps a
      complemented XOR fold of the three context members
      (`debounce_ctx_check_word()`).  Each enabled shell validates a
      local snapshot, computes only from that validated value, and
      then publishes the successor context and fold.  A single-bit
      flip confined to persisted `ctx_` or `ctx_check_` either fails
      validation, is safely overwritten by a transaction already
      based on a valid snapshot, or remains a mismatch for the next
      check.  It cannot be consumed and then legitimized by folding
      live corrupt state.  This is a persisted-state guarantee; it
      does not claim coverage of automatic locals, CPU registers,
      code, or control flow.
      The in-range case is not a harmless one: with a press
      threshold of 8 samples, an idle counter whose bit 3 flips
      already reads as a completed press, and would toggle the
      effect with nobody touching the footswitch.
+
NOTE: The checksum is a firmware mechanism rather than an MCU
feature, so its availability follows flash capacity rather than
silicon family:
+
[horizontal]
AVR Classic (ATtiny13a/45/85), ATtiny202, PIC10F322, PIC12F675::
  enabled (`BYPASS_CTX_CHECK`).  PIC10F322 is the binding capacity
  case: 512 words is the smallest budget that still holds the shared
  core, the defensive layer and the fold, which is why the part below
  it does without.
PIC10F320:: *not* enabled.  Its 256-word flash cannot hold the
  shared pure core, so this shell inlines the debounce logic by hand
  and has no `debounce_ctx_check_word()` to call; even the cheapest
  in-line fold overflows the relay variant.  The range check still
  applies, so out-of-range corruption is caught here exactly as on
  every other part -- only the in-range case goes undetected.  The
  exclusion is deliberate rather than an oversight: the mutation
  suite scans this shell on every run and fails if it ever
  references the context-check machinery, so the difference cannot
  be silently erased in either direction.

    * Fail-safe relay resynchronization: an unexpectedly energized
      relay coil is treated as a fault, never cleared quietly.  The
      intended stray pulse is bounded to about one tick, which is
      below the Panasonic TQ2-L2-5V 4ms minimum for guaranteed
      actuation -- but below the guaranteed-actuation minimum is not
      proven mechanically harmless, so the firmware cannot know
      whether the latching relay moved.  Silently clearing it would
      therefore risk leaving the audio route permanently disagreeing
      with the effect state and the LED.
+
      So the sanity gate escalates it.  The forced-reset path drives
      both coil-control outputs to idle *before* it spins, so no
      fault holds a coil energized for a whole watchdog period, and
      the recovery re-runs initialization.  Initialization sets logical
      state and LED to BYPASS and commands a nominal 12ms RESET-coil
      pulse with SET inactive.  This is the firmware's electrical
      recovery guarantee.  Physical relay convergence additionally
      requires the board, driver, supply and relay assumptions recorded
      in `docs/relay_coil_fault_correction.md`.
+
      Detection reuses each shell's existing output-state integrity
      check, so an energized coil is simply an output-latch
      mismatch.  PIC10F320 cannot afford that general check within
      256 words and instead guards exactly the two coil latch bits,
      giving it full parity on the coil guarantee while retaining its
      documented gap for other output-latch upsets.  Only PIC12F675
      compares physical GPIO against an independent output shadow;
      the other parts do not claim universal external stuck-pin
      detection.
+
      A low output latch is not by itself a physical-pad guarantee when
      pin configuration is corrupt.  AVR-XT can invert a coil pad through
      `PORTA.PINnCTRL.INVEN`; PIC12F675 can route comparator `COUT` onto
      GP2, outside GPIO ownership.  Their forced-reset paths therefore
      wrap the shared latch clear in an MCU-specific emergency sequence.
      AVR-XT removes pull-ups, disconnects direction, clears inversion and
      stale OUT state, then restores the low outputs.  PIC12F675 removes
      coil pull-ups, changes the pins to inputs, disables analog and
      comparator ownership, clears shadow/GPIO, then restores output
      direction.  Board fail-safe pull-downs hold the pins inactive during
      the brief input interval.
+
      Target fault tests observe modeled package pins rather than inferring
      them from latches: physical PA2/PA3 on AVR-XT and direct GP1/GP2 node
      voltage on PIC12F675.  The latter covers every comparator mode one
      bit from off and both comparator output states where COUT can own
      GP2.  Latch-only mutants are rejected.  This is simulator electrical
      evidence; it does not validate PCB loading, silicon behavior or relay
      mechanics.
+
      Relay coil clears use one masked target operation.  On
      PIC12F675 this clears both coil bits in the SRAM shadow before
      one whole-port GPIO write, preventing a corrupt uncleared coil
      bit from being replayed as an intermediate physical high while
      preserving the required all-port refresh.
+
      That single write publishes every shadow bit, not only the coil
      bits, so on PIC12F675 the emergency path also canonicalizes the
      parked spare output GP4 in the shadow first.  Without it the
      escalation would itself convert a corrupt GP4 intent bit from
      inert SRAM into a driven pad and hold it for the whole watchdog
      period, on a pin the board contract permits only while it is
      low.  A second single-pin write is not an alternative: two
      sequential whole-port writes reintroduce the coil replay the
      one-write rule above exists to prevent.  Target fault tests
      sample the GP4 pad at the watchdog spin, where the hazard is;
      a post-reset read cannot see it, because the reset is what ends
      it.
+
      No gate runs during the complete blocking relay actuation
      sequence, from its pre-pulse clear through its post-pulse
      clear.  An upset in that sequence can shorten the intended
      pulse or energize the inactive or both coils.  The
      characterized cases cover 1, 6 and 11ms inside the 12ms delay,
      not every instruction boundary around assertion and clearing.
      The normal epilogue commands both coil outputs low if execution
      completes, but missed or spurious relay actuation, audio
      disruption, and an external output path that does not accept
      that command remain residual risks.
+
NOTE: This trade-off is deliberate and worth stating.  A stray coil
upset now causes watchdog recovery and an unconditional firmware
command to BYPASS.  On conforming hardware that can cause an audible
interruption and physically return the relay to BYPASS even when the
stray pulse would not have moved it.  That price is accepted because
the alternative -- silent correction -- depends on the unsubstantiated
assumption that a below-minimum stray pulse is mechanically harmless.
Faults inside the actuation sequence remain outside every guarantee
above.  See `docs/relay_coil_fault_correction.md` for the physical
convergence assumptions.


== Watchdog Pet-to-Pet Budget

The watchdog is a liveness proof: reaching the pet is what says the
loop is still running.  What the watchdog period therefore has to
cover is not the length of any one delay constant but the longest
WALL-CLOCK interval a *healthy* loop can spend between two
consecutive pets.  Every shell asserts a conservative upper bound on
that interval at compile time, against its own de-rated watchdog
floor.

The bound is built from four terms.  The three shared ones live in
`WDT_PET_TO_PET_MAX_MS()` in `src/bypass_output_common.h`; each pin
map supplies the per-target values, and the self-contained PIC10F320
shell carries its own copy of both:

[horizontal]
blocking actuation:: the relay coil pulse (12 ms) or the
  mute-before-switch settle (5 ms).  Zero on the simple CD4053
  variant, which performs no blocking actuation at all.
ISR preemption (`WDT_ISR_STRETCH_PCT`):: on the interrupt-driven AVRs
  the 1 ms tick ISR preempts the busy-wait inside that actuation, so
  the actuation is longer in wall time than the delay body it
  compiles to.  Despite the historical macro name, this input is the
  percentage `p` of _wall time_ the ISR may own, not additive stretch
  relative to foreground time.  It is zero on the polled PIC shells,
  which run with `GIE` clear and have no interrupt service routine to
  preempt anything.
scheduling latency (`TICK_PERIOD_MS`):: the actuation ends at an
  arbitrary point inside a tick, and the next pass is gated on the
  next tick -- IDLE-sleep wake on AVR, the `TMR2IF`/`TMR0` poll on
  PIC.
bounded loop work (`WDT_LOOP_WORK_MS`):: the non-blocking work in the
  window: the sanity gate, the context transaction and the debounce
  step, plus -- on the boot path -- `init()`'s register
  configuration.  One whole tick is the allowance.

If ISR duty is `p`, foreground delay work receives only `100-p` percent
of wall time.  A delay body requiring `B` milliseconds of foreground
cycles therefore contributes this conservative wall-time term:

....
B + ceil(B * p / (100 - p))
....

The build rejects `p >= 100` before the denominator is used.  The
ceiling uses quotient plus nonzero remainder rather than the
overflow-prone `numerator + denominator - 1` idiom, and multiplication
is promoted to 32 bits.  The supported domain is bounded independently:
`B < RELEASE_THRESH < UINT8_MAX` and `p < 100`, so its largest
numerator is only `254 * 99 = 25146`.  At the AVR value `p=25`, the ISR
may therefore add at most `25/75 = 33 1/3%` of the foreground delay,
not 25%.

The boot path is inside this bound rather than beside it: `init()`
arms the watchdog and then performs the same blocking actuation
before `main()` reaches its first pet.  On the variants that do not
block at all, boot is in fact the longest window there is.  Its
blocking half runs with interrupts disabled, so the ISR term is
headroom on that path rather than a cost.

.Table Per-target watchdog pet-to-pet budget (milliseconds)
|===
| Target | Tick | Loop work | ISR duty | Relay | Mute | Simple | De-rated floor

| AVR Classic (ATtiny13a/45/85) | 1 | 1 | 25% | 18 | 9 | 2 | 100
| AVR-XT (ATtiny202)            | 1 | 1 | 25% | 18 | 9 | 2 | 128
| PIC10F322                     | 1 | 1 |  0% | 14 | 7 | 2 | 160
| PIC10F320                     | 1 | 1 |  0% | 14 | 7 | 2 | 160
| PIC12F675                     | 2 | 2 |  0% | 16 | 9 | 4 | 160
|===

NOTE: The inequality is the primary artifact, and it is deliberately
conservative rather than tight.  Simulator and disassembly timing
corroborate the per-target terms; they do not replace the bound,
because one simulated run over one stimulus cannot enumerate every
path.

Two independent gates hold the budget to something real.
`test/test_static_assert_guards.sh` independently calculates the duty
conversion, pins each variant's bound to its exact millisecond, and
proves the ISR-preemption, tick, and loop-work terms are load-bearing:
a watchdog floor set inside the gap between the old `tick + pulse` sum
and the full wall-clock bound must fail the build, and must go back to
compiling the moment the term under test is zeroed.  A negative control
restores the old mixed duty/additive-stretch denominator and requires
the 18 ms relay oracle to reject it.  `test/avr/test_sim.c` then measures
the real Classic-AVR image: it steps
the compiled firmware, records the longest interval between
executions of `wdr` across boot and across toggles in both
directions, and requires the result to fit the same budget the
firmware compiled against -- not merely to fit under the watchdog
floor, which a badly derived constant would also do.

The exact Classic-AVR intervals are results of the source, compiler and simavr
run, so the harness emits them and any durable result belongs in release
evidence rather than this design document maintaining a second current table.
The reviewed budget above and the gate that compares each built image with it
are the stable contract.

The ATtiny202 runs the same code at 2 MHz. Measuring consecutive `wdr`
executions needs cycle-granular instruction stepping -- precisely the mode the
pinned yasimavr's unpatched `SimLoop.run(n)` rewind makes untrustworthy, even
though the pin edges it timestamps from a signal hook are exact (see the
yasimavr note in `test/README.md`). Its term is therefore bounded from the built
image instead. The reviewed ceiling is 84 instructions for the TCB0 ISR and its
callees; charging every instruction four cycles and reserving another 16 cycles
for interrupt entry and vector dispatch bounds the complete response at 352 of
the 2000 cycles in a 1 ms tick (17.6% duty, or at most 21.4% additive stretch).
`attiny202-delay-oracle` recovers the sole `reti` handler and its direct call
tree from every built image and enforces that 84-instruction
ceiling; recursion, unresolved or indirect transfers, and control-flow cycles
fail closed rather than being undercounted; acyclic branches to earlier shared
epilogues remain countable.  Its compiled delay-body oracle and delivered-pulse
trace complete the corroboration without making an untrustworthy full-interval
measurement.
The polled PIC shells have no ISR term to measure.


== Asymmetric Debounce Timing

The design deliberately uses asymmetric timing for debouncing the
switch press and release.  The goal is to use a shorter time window
for press-debounce, so the state change feels instantaneous to the
user.  The release-debounce, or lock-out period, is longer so as to
"hide" additional debounce latency from the user.

    * PRESSED_THRESH upper bound (latency constraint):
      The slow-clock extreme is -10% frequency, so a nominal 1ms tick can last
      1/0.9 = 1.111ms; PIC12F675's nominal 1.024ms tick can last
      1.024/0.9 = 1.138ms. (+10% frequency shortens those ticks to 0.909ms and
      0.931ms respectively; it is the favorable latency extreme, not the worst
      case.) If `N` accepted samples are required, their sample instants span `N-1`
      intervals and an arbitrarily phased physical edge adds less than one
      interval. Ignoring sub-tick instruction overhead, clean edge-to-toggle
      latency is therefore from about `(N-1)*T` to less than `N*T`.
      `PRESSED_THRESH=8` gives a worst-phase, -10%-frequency upper bound below
      8 * 1.111ms = 8.89ms on the 1ms targets and below
      8 * 1.138ms = 9.11ms on PIC12F675. A threshold of 9 would approach 10ms
      with no margin on the 1ms targets and exceed 10ms on PIC12F675; 10 would
      violate the <10ms goal everywhere.
      Bounce or EMI/RFI can subtract counter progress and make recognition take
      longer than this clean-input bound.

    * PRESSED_THRESH lower bound (EMI rejection):
      The RC filter (1k series + 22nF to ground + approx. 7.5k pullup
      effective) has a time constant 22nF × (1k || 7.5k) =
      approx. 18µs. EMI spikes shorter than a few RC time constants are
      attenuated below the Schmitt threshold. The filter provides
      hardware-level rejection of spikes shorter than roughly 100µs.
      `PRESSED_THRESH=8` is a sample-count threshold, not an 8ms persistence
      threshold. Eight low sample instants span seven tick intervals. At the
      +10%-frequency extreme, a favorably phased continuous low pulse just over
      7 * 0.909ms = 6.36ms can therefore be sampled low eight times on a 1ms
      target; the PIC12F675 counterpart is 7 * 0.931ms = 6.52ms. Starting from
      counter zero, any isolated low pulse at the MCU digital input shorter than
      the target's corresponding bound is guaranteed not to register under the
      stated clock tolerance; between that bound and the worst-phase recognition
      bound (less than 8.89ms or 9.11ms), the outcome depends on sample phase and
      oscillator frequency. Noncontiguous low samples can also
      accumulate if intervening high samples do not fully drain the integrator,
      so there is no universal physical "must persist" duration for arbitrary
      noise. Even the guaranteed single-pulse bound is more than 60 times the
      roughly 100us hardware-filter scale.

    * RELEASE_THRESH (minimum lockout before next press):
      At the pure-algorithm sample level, a clean press followed by immediate
      release consumes `PRESSED_THRESH + RELEASE_THRESH = 33` accepted sample
      updates. On the ISR-driven AVR implementations this is a conservative
      nominal 33ms
      qualification budget; physical press-onset-to-re-arm timing is roughly
      32-33 tick periods because 33 sample instants span 32 intervals and the
      first sample has arbitrary phase. For the polled PIC implementations,
      conservative qualification adds the full blocking output actuation after
      the toggle. The PIC10F32x nominal simple/mute/relay budgets are
      33ms/38ms/45ms; PIC12F675's are approximately 33.8ms/38.8ms/45.8ms. A
      pending PIC10F32x `TMR2IF` can make the next sample immediate. A pending
      PIC12F675 `T0IF` supplies one of four 256us rollover observations, so its
      next sample still waits for up to three more. These are robust
      sample-count budgets rather than exact physical minima.

== PIC12F675 DIP-8 Package Pinout

Pin functions transcribed from the device pack's `edc/PIC12F675.PIC`, not from a
datasheet summary.

....
                                +----+
                      V_DD pin1-|    |-pin8 V_SS (GND)
    (T1CKI/OSC1/CLKIN) GP5 pin2-|    |-pin7 GP0 (AN0/CIN+/ICSPDAT)
 (AN3/T1G/OSC2/CLKOUT) GP4 pin3-|    |-pin6 GP1 (AN1/CIN-/Vref/ICSPCLK)
          (~MCLR/V_PP) GP3 pin4-|    |-pin5 GP2 (AN2/T0CKI/INT/COUT)
                                +----+
....

This is **not** the PIC10F32x assignment renamed. Three differences are forced
by the silicon:

* **The footswitch is on GP5, not on the input-only pin.** The 322's map rests
  on a coincidence — its RA3 is both input-only *and* pull-up capable. Here the
  `WPU` register implements bits 0, 1, 2, 4 and 5 only: GP3 has no internal weak
  pull-up at all. Putting the footswitch there would make an external pull-up
  mandatory and would delete the runtime pull-up integrity check from this
  target. GP5 is also the one bidirectional pin with no analog function, so no
  `ANSEL` or `CMCON` upset can silently re-analogize it.
* **GP4 is a parked output, not an unconnected spare.** It is driven low and
  included in the guarded output mask, so the board must leave it unconnected or
  connect it only to a load that is safe while driven low. GP3 remains an input
  and needs an external pull-up compatible with ICSP/V_PP programming.
* **GP2 must read back as a logic high when it is driven high.** Having no
  output latch, the shell keeps an SRAM shadow and re-reads GPIO against it
  every tick, so the output pins' *input* thresholds become a board requirement
  — and GP2 is the only output here whose input buffer is a Schmitt Trigger
  (VIH min 0.8 x VDD) rather than TTL (VIH min 2.0 V). A GP2 held high that
  reads back below 0.8 x VDD trips the integrity check and the part resets
  forever. This binds `cd4053_with_mute`, the one variant that holds GP2 high in
  a checked state: `cd4053_simple` leaves it a spare driven low, and the relay
  variant raises it only during the blocking coil pulse, which no integrity
  check straddles. Both board options clear the requirement by a wide margin —
  the pin drives a MOSFET gate or a CMOS control input, and the only resistive
  load is the 100k fail-safe pulldown — but a substituted low-value pulldown, or
  anything else hung off GP2, has to respect it.
+
The numbers are one-sided, which is why the requirement is written down rather
than assumed. DS41190G Table 1-1 makes GP2 the only Schmitt-Trigger input among
this design's outputs: D041 gives it VIH min 0.8 x VDD, 4.0 V at a 5 V supply,
where D040 gives the TTL buffers on GP0, GP1, GP4 and GP5 VIH min 2.0 V. The
drive side is characterized at a single point -- D090, VOH min VDD - 0.7 V at
IOH = -3.0 mA and VDD = 4.5 V, which is 3.8 V against a 3.6 V threshold, 0.2 V
of margin -- and nothing at all is specified above 3 mA. The 100k fail-safe
pulldown draws 50 microamps at 5 V, roughly 60x inside that characterized
point, so the reference boards are not close to the limit; a substituted
low-value pulldown could be. No lane here can see it either way, because gpsim
models pins ideally, so the loaded-board measurement is a bench item --
`HARDWARE_VALIDATION_LOG.md`, "Outstanding controlled runs".

LED on GP0, control/coil pins on GP1 and GP2 — the same roles the 322 gives RA0,
RA1 and RA2.


== ATtiny202 SOIC-8 Package Pinout

The ATtiny202 is **not available in a through-hole DIP package** — SOIC-8 and
UDFN-8 only. Of its eight pins, six are I/O: PA4 and PA5 exist in the die's
PORTA register but are not bonded out on the 8-pin package.

Physical pin numbering below is taken from the `SOIC8` pinout in Microchip's own
`ATtiny202.atdf` device file, as shipped in the pinned ATtiny_DFP the build uses
(see `TOOLCHAIN.adoc`) — not from a redrawn diagram. The vendored four-file DFP
subset does not include the `.atdf`, so re-checking this means reading it out of
the full atpack.

....
                                        +----+
                               VDD pin1-|    |-pin8 GND
               (AIN6/spare)    PA6 pin2-|    |-pin7 PA3 (AIN3/EXTCLK/CTL2/relay SET)
       (AIN7/footswitch input) PA7 pin3-|    |-pin6 PA0 (UPDI/~RESET)
             (AIN1/status LED) PA1 pin4-|    |-pin5 PA2 (AIN2/CTL1/relay RESET)
                                        +----+
....

Pin roles in this design map one-for-one onto the AVR Classic assignment above:

    * PA7: input; footswitch, internal pull-up, normally high, pulled low when
      pressed (the classic shell's PB0)
    * PA1: output; status LED, high when engaged (PB1)
    * PA2: output; x4053 control / relay RESET coil (PB2)
    * PA3: output; x4053 second control / relay SET coil (PB3)
    * PA6: output driven low.  It is otherwise unused; driving it low rather
      than leaving it an input keeps it from floating, and it is included in the
      exact-direction and output-latch integrity checks (see Failsafe
      Mechanisms) so a corrupted PORTA is still detected on that bit.
    * PA0: left as UPDI (the `RSTPINCFG` field of `SYSCFG0` keeps it as the
      programming pin).  It is never used as GPIO, which is why the design fits
      an 8-pin part without sacrificing the programming interface.

`src/bypass_pins_avr_xt.h` is the single source of truth for these assignments;
`bypass_mcu_avr_xt.c` pins each of them to `<avr/io.h>`'s generic `PINn_bp`
constants with compile-time asserts, so a typo in the map cannot misroute a pin.

NOTE: unlike the classic AVR parts, PA7 here is deliberately placed well clear
of the UPDI pin.  Putting the footswitch on PA0 would have shared it with the
programming interface.


== Optimal Footswitch-GPIO Wiring for EMI/RFI resiliency

The GPIO pin tied to the footswitch (normally high) will have some
hardware-level EMI/RFI protections and also aid with debounce.
Wiring is as follows:

Footswitch lead 1: GND

Footswitch lead 2 ("FOOTSW_PIN"):

    * TVS diode to ground (cathode=signal, anode=GND)
    * series ferrite bead
    * series 1k resistor ("a" side to FB, "b" side to "node b")
    * 22nF capacitor "node b" to ground (close to MCU GPIO pin)
    * 10k pullup resistor "node b" to VCC

Wiring diagram:
....
                                       VCC(5v)
                                          |
                                        [10k]
                                          |
  FOOTSW_PIN -----+-----[FB]-----[1k]-----+-----GPIO_PIN
                  |                       |
               [TVS-K]                 [22nF]
               [TVS-A]                    |
                  |                       |
                 GND                     GND
....

Note this wiring is overbuilt for the intended purpose.  All parts
are recommended for best EMI/RFI resiliency, but for non-adverse
environmental conditions and/or prioritizing reduced BOM cost and
PCB space, the TVS diode and ferrite bead can be omitted.


== CD4053 Notes

    * the newer TMUX4053 switches can be controlled with logic
      levels lower than the voltage supply (e.g. CMOS, TTL)
    * the older CD4053 needs logic "true" to be the same level as
      the voltage supply
    * the AVR Classic MCU will run at 5v, but the 4053 will run at
      the effect voltage (9 to 18 volts)
    * 5v rail derived via LP2950 for through-hole implementation
      or AP7375 for SMD implementation
    * 5v rail only for MCU and footswitch - everything else
      (including status LED) is powered from the parent 9-18v rail
    * therefore, the 4053 control pins will be held to effect
      voltage via pullup resistor; the control pins will be pulled
      low (to ground) via a mosfet; that mosfet's gate will be
      controlled by AVR PB2
    * therefore, the PB2 pin value is actually inverted at the
      CD4053:
        ** PB2 high -> mosfet on -> 4053 control pins low
        ** PB2 low -> mosfet off -> 4053 control pins high
    * the 4053 is wired such that:
        ** control pins high = bypass
        ** control pins low = engaged
    * assume 2n7000/2n7002 mosfets for CD4053 control and LED
      control

=== CD4053 vs TMUX4053 Notes

    * CD4053 available in through-hole and surface-mount
    * TMUX4053 surface-mount only
    * TMUX4053 can use lower-voltage logic true (e.g. CMOS, TTL)
    * CD4053 needs logic true to be at VDD
    * VDD will be effect voltage (typically 9-18v)
    * Two board options, one firmware image:
        ** CD4053 (control logic at VDD, typically 9-18v): the 5v MCU
           cannot drive the control pins directly, so each control pin is
           held HIGH via a pullup to VDD and pulled LOW through a MOSFET
           whose gate the MCU drives. This inverts the MCU signal:
           MCU high -> switch control low; MCU low -> switch control high.
        ** TMUX4053 (logic-level control, e.g. CMOS/TTL): the MCU drives
           the control pins DIRECTLY. Each control pin has a pulldown to
           GND, so MCU low -> switch control low; MCU high -> switch
           control high. There is no MOSFET.
    * Fail-safe by design: the natural state, with the MCU pins undriven
      (they sit at their pulldown level, i.e. low), must be BYPASS. For the
      CD4053 the MOSFET is then off and the control pins sit HIGH; for the
      TMUX they sit LOW. The TMUX board therefore SWAPS its analog throws
      (A0/A1, B0/B1, C0/C1) relative to the CD4053 so that both parts land
      in BYPASS from their opposite rest levels (see the per-part truth
      tables below).
    * Consequence: the CD4053's MOSFET inversion and the TMUX's swapped
      throws cancel, so the MCU drives an IDENTICAL polarity for both parts
      (BYPASS = pin low, ENGAGE = pin high). A single firmware image
      (`cd4053_simple` / `cd4053_with_mute`) drives BOTH boards -- there is deliberately no
      separate TMUX build. (An earlier revision shipped separate _tmux
      images that re-inverted the MCU drive; because the hardware already
      cancels the difference, that was a latent polarity bug and the
      variants were byte-identical once corrected, so they were dropped.)

| Sleep wake-up ordering
| one instruction executes after `SEI` before the pending interrupt is serviced
| ATtiny13A datasheet **§7.3**
| **Documented implementation rationale.** The sleep-entry comment in

| DS41190G **Table 12-2 param F10** `FOSC` (+/-1% at 3.5 V/25 degC, +/-2% over

== Resource Utilization

What each part physically holds, the ceiling every build enforces against it,
and how the figures are measured.

This section carries no current measurement, deliberately. Exact per-image
flash, static-data and stack figures are release evidence: they are bound to a
source commit and a pinned toolchain in `release/<version>/MANIFEST.md` and in
the retained `release/<version>/evidence/resource-tables.log` that produced
them. Restating them here would make a documentation edit a precondition for a
firmware size change, and would leave the copy wrong in the interval — which is
what happened, repeatedly, while these tables existed.

Every ceiling below is declared once, in the `Makefile`, and enforced on every
build of the part it bounds, so an overshoot fails the build rather than
reaching hardware. `make test-resource-tables` measures every image the tree has
already built against those declarations; the production release runs its strict
form over the complete canonical image set and RAM/stack logs, retains its
source-commit-bound result, and refuses to stage otherwise.

To see what the working tree currently occupies, build it and read the build's
own report: `make attiny13a-size` reports Classic AVR `Program:` and `Data:`
bytes, and `make attiny202`, `make pic10f322`, `make pic10f320` and
`make pic12f675` each print per-variant usage against the ceiling as they gate
it. Those reports are ephemeral by design — they describe the tree you have, not
a released image.

=== Units and methods

The unit is part of the figure. AVR flash is counted in BYTES by the linker;
PIC flash is counted in fourteen-bit PROGRAM WORDS by XC8, and reporting either
in the other's unit is the mistake this pairing exists to prevent. RAM figures
are always bytes.

Three distinct RAM quantities appear in this project, and they are not
interchangeable:

* *Static data* — what the build allocates before `main()` runs. Reported by
  `avr-size` as `Data:` on the AVR parts and by XC8's Data-space summary on the
  PIC parts, the latter including statically overlaid automatic storage.
* *Per-function stack frame* — the largest single frame any function needs,
  derived statically from GCC's `-fstack-usage` reports. It bounds one frame,
  not a call chain.
* *Whole-path stack high-water mark* — the deepest the stack actually reached
  while executing the deepest paths, measured empirically. On the Classic AVR
  parts the simavr canary test measures it directly; on the PIC parts the
  equivalent quantity is hardware return-stack depth in levels, measured from
  the emitted assembly and re-derived independently from the shipped HEX.

A frame bound is not a high-water mark, and the release evidence records which
of the three each figure is.

=== AVR Classic family

Static data comprises `timer_isr_called_` (1 byte, shared between main and the
timer ISR), `ctx_` (the 3-byte `debounce_context_t`), and the 1-byte
`ctx_check_`. Peak stack is the empirical high-water mark measured by the simavr
stack-canary test (see Testing and Validation above).

Free SRAM on these parts is a deliberate design property rather than a
leftover, and it is gated rather than merely stated:
`test_stack_high_water_mark()` in `test/avr/test_sim.c` paints SRAM with a
canary, exercises the deepest call paths, and fails
`make test-sim-attiny13a` unless at least 8 free bytes separate the deepest
stack pointer from the top of the static data. The top of static data is read
from the firmware ELF's `__bss_end` rather than assumed, so a future static
variable tightens the gate on its own; if that symbol cannot be resolved the
test fails rather than falling back to a looser reference point.

Flash, not SRAM, is the tighter resource on the ATtiny13a, and it has its own
gate: `make test-flash-budget` holds every variant to
`ATTINY13A_FLASH_BUDGET` percent of the device, computed by integer truncation,
so the default 90% of 1 KB is a 921-byte limit and not 921.6. Within this family
that percentage gate covers the ATtiny13a, the part it binds: on the tinyx5
parts the same firmware occupies a fifth or a tenth of the device, so the
linker's device size is the bound those builds need. Each ATtiny45 image is the
same size as its ATtiny85 counterpart and slightly larger than the corresponding
ATtiny13a image; the two are not byte-identical, because each is linked for its
own device.

=== ATtiny202 (AVR-XT build)

The ATtiny202 has 2 KB of flash and 128 bytes of SRAM — roughly double the
ATtiny13a on both — so it is the least constrained AVR part in the set. Flash
figures are reported by the build itself (`make attiny202`), which gates every
variant against `XT_FLASH_BYTES` and holds static `Data:` use to
`XT_STATIC_RAM_LIMIT` of the device's `XT_SRAM_BYTES`, leaving the remainder for
the runtime stack and interrupt context. They do not come from `avr-size`'s
device-aware percentages: binutils 2.26 does not recognise `avrxmega3` parts, so
`avr-size -C --mcu=attiny202` reports "Device: Unknown" while still reporting
the exact `Program:` and `Data:` byte counts the gate consumes.

The AVR-XT shell keeps the same static objects as the AVR Classic shells and for
the same reason: `ctx_`, `ctx_check_`, and the `timer_isr_called_` ISR-to-main
handshake.

`attiny202-test-stack-bound` compiles `bypass_mcu_avr_xt.c` under every
immutable production selector with the shipping flags plus `-fstack-usage` and
rejects any frame above `XT_STACK_MAX_FRAME`. `test-stack-bound` continues to
cover the shared core and drivers. These gates bound individual compiler frames,
not the complete call-chain plus interrupt high-water mark. No AVR-XT lane
measures that maximum — the stack-canary test is a simavr/AVR Classic lane — so
the actual per-variant maxima remain unretained and must be measured before this
part is qualified on hardware.

=== PIC10F322 (XC8 build)

The PIC10F322 port has a much tighter device budget, 512 fourteen-bit program
words and 64 bytes of RAM, so its figures are reported in words by the XC8
compiler, not bytes. `make pic10f322` enforces `PIC10F322_FLASH_WORDS` per
variant on every build, so an overshoot fails before hardware.

Flash is the binding constraint on this part, and it is binding by a margin thin
enough to be a design input rather than a footnote: it is why the
integrity-check fold in `docs/context_seu_detection.md` had to be spelled the
compact way, and why any rewrite of those functions must be re-measured against
the gate rather than assumed free. That document holds the reasoning and the
measured cost of each alternative spelling.

Persistent firmware state comprises `ctx_` and `ctx_check_`; the PIC's polled
Model-B loop has no `timer_isr_called_` handshake. An exact whole-program XC8
Data-space total is not published for this target: the release retains its flash
and return-stack measurements but does not yet retain a Data-space record that
can support that claim.

=== PIC10F320 (XC8 build)

The PIC10F320 is the same silicon family with **half** the flash: 256
fourteen-bit program words. It is the smallest-capacity supported part and the
reason its firmware is structured differently from every other target (see
<<pic10f320-architecture>>). `make pic10f320` enforces
`PIC10F320_FLASH_WORDS` per variant and fails the build on any overshoot.

The persistent firmware state is `ctx_`. An exact whole-program XC8 Data-space
total is not published for this target for the same evidence reason as the
PIC10F322: flash and both return-stack witnesses are retained, but no release
record currently binds a Data-space total to the qualified source.

Its margins are the whole story of this target, and they are the reason for
decisions recorded elsewhere rather than a number to restate here. The general
output-latch integrity check was priced against an earlier image, exceeded the
budget on two variants, and remains unported; the exact-`TRISA` check and the
relay-only coil-latch term were affordable and were ported. Going the other way,
making the relay's coil clear a single masked `LATA` write returned words by
removing two per-bit helpers that had no other caller. That does not by itself
reopen the latch-check question — `cd4053_with_mute`, which is unaffected by any
of it, is the variant the check overflowed first — but a re-pricing would start
from a different number than the one it was refused on.
<<pic10f320-architecture>> records those decisions; the measurements each was
made against belong to the release record.

=== PIC12F675 (XC8 build)

The PIC12F675 is the roomiest PIC here: 1024 fourteen-bit program words, 64
bytes of RAM, plus 128 bytes of data EEPROM the firmware does not use.
`make pic12f675` enforces `PIC12F675_FLASH_WORDS` and an inclusive
`PIC12F675_DATA_LIMIT` of the device's `PIC12F675_DATA_BYTES` per variant. The
latter preserves allocation headroom and includes XC8's statically overlaid
automatic storage.

Persistent firmware state comprises `ctx_`, `ctx_check_`, `gpio_shadow_` (the
software output latch this core needs), and `osccal_snapshot_` (the factory
oscillator trim captured at init). The build requires one internally consistent
XC8 summary per variant and fails above the reviewed Data-space limit. The
PIC10F322 needs neither of the final two objects: it has a real output latch and
compares `OSCCON` against a compile-time constant instead of a captured value.

The comfortable flash margin here is a consequence of the part, not of a leaner
build. The comparison that isolates it is `tq2_l2_5v_relay`, which compiles the
same core and the same driver on both parts; the difference is shell, and it
buys the work this core makes necessary — turning off a comparator and an ADC
the 32x parts do not have, routing every output write through the shadow, and
counting four timer rollovers in software to make the tick. Twice the PIC10F322's
flash is the reason the modular architecture fits here at all.

== Multi-MCU Architecture: Shared Core, Per-MCU Shell

The implementations span four core generations -- AVR Classic, AVR-XT,
enhanced mid-range PIC10F32x, and classic mid-range PIC12F675 -- that share one
debounce design but differ at the register level. Most use the modular
architecture, with shell ownership separated by peripheral family:
`src/bypass_mcu_avr_classic.c` serves ATtiny13a/45/85,
`src/bypass_mcu_avr_xt.c` serves ATtiny202,
`src/bypass_mcu_pic10f322.c` serves PIC10F322, and
`src/bypass_mcu_pic12f675.c` serves PIC12F675. PIC10F320 is the
self-contained implementation described below. The modular split has two rules.

**The modular targets share one compiled core.** `src/bypass_pure.c` is
the functional core: no hardware access, no globals, no side effects. Every
modular target compiles and links that same file, and the core host tests and
formal proofs exercise it directly. Nothing about it is per-MCU. PIC10F320 does
not compile it into its image; equivalence and lock-step compare the
self-contained firmware with this same core.

**The main loop is NOT shared.** Each modular shell file owns its own `main()`,
tick mechanism and watchdog-liveness model; the self-contained PIC10F320 file
owns its own. Only the modular output-driver leaf operations are
abstracted. This is deliberate: one portable `main()` parameterized by an
interface looks cleaner and is wrong here.

The AVR Classic design samples the footswitch *inside* the 1 ms Timer0 ISR
while `main()` sleeps, and proves liveness through the `timer_isr_called_`
ISR-to-main handshake. The PIC implementations use a fundamentally
different model: no tick ISR, but a polled loop that waits on a timer flag,
samples, updates and pets the watchdog, where reaching `CLRWDT` *is* the
liveness proof. The PIC10F322 and PIC12F675 versions are modular shells;
PIC10F320 writes the same model into its self-contained source. The flag is not
the same one: the 10F32x parts wait on a single `TMR2IF` per 1 ms tick, while
the PIC12F675 counts four `T0IF` rollovers per 1.024 ms tick, for the reason
given above. A single shared `main()` cannot express both timing
models without changing AVR's ISR sampling and invalidating lock-step,
ISR-jitter and handshake tests.

The ATtiny202 follows the AVR Classic model rather than the PIC one, but on
entirely different peripherals: the tick is TCB0 in periodic-interrupt mode
(`CCMP` = 1999 at 2 MHz) instead of Timer0 compare-match, the sleep is AVR-XT
IDLE via `SLPCTRL`, and the watchdog is fuse-locked by `WDTCFG` so `hw_wdt_pet()`
is a bare `wdr` with nothing to arm. Because it integrates in the ISR, it
shares the classic lane's blocking-actuation timing property: the ISR keeps
sampling through a blocking relay or mute pulse, so no ticks are lost. The AVR
generations and polled PIC implementations therefore have different
release/re-arm timing on the blocking
mute and relay variants (see Asymmetric Debounce Timing); PIC12F675's 1.024ms
tick separately lengthens every sample-count-derived wall-time figure. This is
the clearest illustration of why the modular shells are separate: AVR-XT and AVR
Classic share a *model* and none of their register code.

So `main()`, the tick source, `init()` as orchestrator and the reset path stay
file-static inside each implementation. The consequences are visible elsewhere
in this document: the polled PIC implementations pause sampling during a
blocking output actuation while both ISR-driven AVR generations continue (see
Asymmetric Debounce Timing), PIC12F675 has the distinct 1.024ms cadence, and no
PIC carries a `timer_isr_called_` byte (see Resource Utilization).

**What the shared interface does cover.** `src/bypass_hw_iface.h` is the
*output-driver* boundary only: the GPIO leaf operations a shell provides to a
driver (`hw_pin_set_*`, `hw_led_pin_set_*`, `hw_configure_output_pins`,
`hw_output_state_intact`) and the operations a driver provides back
(`hw_set_bypass_state`, `hw_set_engaged_state`, `hw_is_sanity_check_failed`,
`hw_init_output_pins`). The pin-direction API is mask-based so one driver body
serves every modular target: the AVR Classic implementation writes `DDRB`, the
AVR-XT one writes `PORTA.DIR`, the PIC10F322 shell maps the mask onto `TRISA`,
and the PIC12F675 shell maps it onto `TRISIO` — and, having no `LATx`, applies
every level change to an SRAM shadow and then copies the shadow to `GPIO`,
because a read-modify-write against `GPIO` would read back *pin* levels rather
than the last value written. PIC10F320 does not consume this interface or the
modular drivers.

In the modular architecture, everything else — footswitch read, watchdog arm
and pet, clock and peripheral bring-up, wait-for-tick, the forced-reset path,
and the SFR integrity checks — is shell-private and rewritten per shell. That
is not an oversight: MISRA
Rule 8.7 flagged the earlier arrangement, since each of those helpers is
referenced only within its own translation unit. Adding a target normally means
adding a shell plus a pin map, and reusing the core and all three output
drivers unchanged. No existing shell needs to be refactored.

=== The one target that does not follow this rule

The PIC10F320 is the exception, and it is worth naming here rather than leaving
the paragraph above to be read as universal. It has **256 words of flash, half
the PIC10F322's**, so the shared-core-plus-shell arrangement does not fit and
its firmware is a single self-contained file that links neither the core nor
the output drivers. That trades the compile-the-verified-core property for a
direct behavioural comparison against that same core, plus orthogonal fault,
actuation, coverage, static-analysis, byte-identity and soak evidence. It first
shipped in the unified `v0.9.6` release and remains release-supported.

<<pic10f320-architecture>> is the normative account: why 256 words forces the
architecture, what the resulting seam is, what closes it and how far, and what
remains unequal.

== PIC Architecture

The PIC implementations are not configurations of one shell. PIC10F322 and
PIC10F320 are enhanced mid-range
cores from a single datasheet family (DS40001585); PIC12F675 is a classic
mid-range core (DS41190G) whose register set differs from theirs at nearly
every point this firmware touches. PIC10F320 then differs from PIC10F322 not
in silicon generation but in capacity, and that one number changes its
software architecture rather than its register code.

What they do share is one behavioural model. This section states that
model once, then states what each part does differently and why, so that every
target-specific difference has exactly one normative explanation.

What it deliberately does not carry: package pin diagrams are in the pinout
sections above, watchdog margin arithmetic is in Watchdog Pet-to-Pet Budget,
sample-timing budgets are in Caveats and Limitations and Asymmetric Debounce
Timing, defensive-layer behaviour common to every target is in Failsafe
Mechanisms, compiler and device-pack versions are in `TOOLCHAIN.adoc`, the
operator programming transaction is in `FLASHING.md`, hardware qualification
is in `HARDWARE_VALIDATION_LOG.md`, and measured image sizes and test results
belong to retained release evidence rather than to prose.

[[pic-model-b]]
=== The shared model: polled tick, pure fault watchdog

The PIC implementations use the model this project calls **Model B**: a
polled hardware timer tick, with the watchdog kept as a pure fault watchdog
and no timer interrupt. `init()` configures the part, applies the bypass
output state and starts the tick timer; the loop then waits on the timer flag,
runs the sanity gate, samples the footswitch, integrates, applies the debounce
step, and pets the watchdog. Reaching the pet **is** the liveness proof: there
is no ISR-to-main handshake to carry one, because there is no ISR.

The alternative considered was a watchdog-periodic-wakeup loop -- sleep, wake
on the watchdog, sample, update, sleep. Model B was chosen for three reasons,
and each of them is still load-bearing:

. **It matches the AVR design more closely.** The same nominal 1 ms sampling
  cadence, polled rather than interrupt-driven, so one debounce design covers
  both families and the pure core is untouched.
. **It dissolves the blocking-actuation conflict.** The longest awake burst a
  healthy loop can produce -- one tick wait plus the 12 ms relay coil pulse or
  the 5 ms mute settle, plus bounded loop work -- fits inside one de-rated
  watchdog period with a wide margin. The shared output drivers therefore keep
  a plain blocking delay and no watchdog-aware delay abstraction exists. The
  per-target arithmetic is in Watchdog Pet-to-Pet Budget.
. **It dissolves the shared-state hazard.** One execution context means nothing
  is shared: `ctx_` is owned solely by `main()`, no field has to be readable
  and writable in a single uninterruptible instruction, and no PIC carries a
  `timer_isr_called_` byte. This is why XC8 sizing enums as `int`, where the
  AVR builds rely on `-fshort-enums`, is harmless here.

Converting a PIC shell to a timer ISR was later priced on the real toolchain
and rejected again. The conversion was applied to the shipping PIC10F322 shell
-- ISR, handshake flag, `volatile ctx_`, and a flag protocol replacing the
timer-flag poll -- and rebuilt. The relay variant did not link: the linker
needed a two-word contiguous range and the largest free one was a single word,
which is fragmentation at a full ceiling rather than a program two words too
large. Freeing flash would not have settled it either, because that call shape
consumes six of the eight hardware return-stack levels, leaving nothing beyond
the deliberate two-level reserve. Those are dated 2026-08-05 figures for a
spike build that was never shipped, not a measurement of any current image;
what carries forward is the conclusion, which is that Model B is now held in
place by the budget as well as chosen on merit.

The PIC12F675 is the one part where that budget argument does not apply, and
the answer there is weaker on purpose. Its flash headroom is large enough that
an AVR-shaped ISR spike compiled, linked and ran the tested gpsim trajectory --
the thing the PIC10F322 relay conversion could not do -- so the model was never
ruled out by size on this part. What was never obtained is the number that
would decide it: the bound is main's deepest chain plus the ISR's plus one,
against the same 8 levels and the same two-level reserve, and no PIC12F675 ISR
source, assembly or gate result was retained. Model B therefore stands here by
consistency with the other two shells and by the absence of a reason to change,
not by a measurement, and any future attempt should produce the retained stack
result first, because the answer constrains the shell's call graph rather than
a test.

Two consequences are accepted rather than mitigated, and both are stated
elsewhere in this document because they are user-visible:

* **No low-power sleep.** The loop is always awake, which makes the core clock
  the thing that sets current draw -- see <<pic-clock-and-power>>.
* **Sampling pauses during a blocking output actuation.** The footswitch is not
  sampled for the 12 ms of a relay coil pulse or the 5 ms of a mute settle,
  where both AVR generations keep integrating inside their timer ISRs. The
  toggle itself is never at risk, because actuation begins only after the
  press has been accepted; what moves is release recognition. See Caveats and
  Limitations and Asymmetric Debounce Timing for the resulting budgets.

A note for anyone tempted to add an ISR later: these are 8-bit cores with no
atomic multi-byte access, so a future revision that shared a multi-byte object
between an ISR and `main()` would have to add explicit protection. Note also
that `INTCON` is deliberately absent from every PIC guard set. Under Model B
the hazard is an upset that **enables** interrupts where no handler exists, and
since no enable bit is ever set by the firmware, reaching a vector costs two
coincident flips -- outside a single-event threat model.

[[pic-clock-and-power]]
=== Clock choice and current draw

Applies to both PIC10F32x parts: they share a datasheet family, a clock choice
and a main-loop model. The PIC12F675 shares the model and differs in the
numbers; see the note at the end of this section.

The PIC core runs at **2 MHz** (HFINTOSC) on a **polled 1 ms tick** — a busy-wait
on `TMR2IF`, never asleep. This is the opposite of the AVR Classic design, which
sleeps between ISR-driven samples, and it is deliberate. The PIC10F320/322 has no
idle mode, and its only Sleep-capable periodic wake is the coarse WDT (TMR0/TMR2
are FOSC/4-clocked and stop in Sleep), so a *precise nominal* 1 ms cadence
necessarily means staying awake. The design spends that power to buy a
timer-derived nominal cadence and a high-margin, independent watchdog; a
deep-sleep scheme would have to give up one or both.

Because the loop is always awake, the clock frequency sets active current. The
core is clocked at 2 MHz rather than the part's 16 MHz maximum, leaving 500
instruction cycles in each nominal millisecond. Exact loop cost depends on the
source and compiler, so the image timing and watchdog gates prove the required
headroom instead of this document maintaining a current cycle count. Datasheet
DS40001585 parameters D017-D019 establish that the lower clock also lowers
typical active supply current; no bench current measurement is claimed here. A
lower clock also emits less high-frequency switching noise into the analog
audio path.

This firmware is **not** battery-optimised: in a typical pedal the always-on
status LED and the analog signal path dominate the supply, so the MCU's active
draw is usually not the binding battery load. The 2 MHz choice avoids
unnecessary active current while retaining the timer and watchdog margins the
executable gates enforce.

**The PIC12F675 makes the same trade with different numbers.** It is also always
awake, but its oscillator is fixed at 4 MHz in silicon by `FOSC=INTRCIO` — there
is no `OSCCON` and nothing to select at runtime — so the clock is not a design
variable on that part. Its tick is 1.024 ms rather than 1 ms because the core has
no period register and one shared prescaler that goes to *either* the timer or
the watchdog: giving it to the watchdog leaves TMR0 unprescaled at F_OSC/4, and
four 256 us rollovers counted in software make the tick. The 2.4% stretch changes
nothing in the debounce core, which counts samples rather than milliseconds, but
it moves every physical timing figure — see <<pic12f675-architecture>>.

[[pic10f322-architecture]]
=== PIC10F322: the reference PIC shell

The PIC10F322 carries the full defensive layer, and it is the shell the other
PIC implementations are described against. It is a modular target:
`src/bypass_mcu_pic10f322.c` and `src/bypass_pins_pic10f322.h` sit on top of
the shared output drivers and compile and link `src/bypass_pure.c` unchanged.

**Four I/O pins, and the map falls out of that.** `RA0`, `RA1` and `RA2` are
bidirectional; `RA3` is input-only, sharing the MCLR/VPP function. With
`MCLRE=OFF` the footswitch therefore goes on RA3, which frees all three
bidirectional pins for outputs: RA0 drives the status LED, RA1 and RA2 carry
the analog-switch control lines or the two relay coils. The map rests on RA3
being both input-only **and** pull-up capable -- a coincidence of this family
that PIC12F675 does not repeat. The relay and mute variants use all three
output pins with none spare; `cd4053_simple` leaves RA2 driven low as a spare,
which the integrity checks still cover.

**The tick is configured, not constructed.** TMR2 counts against the `PR2`
period register with the postscaler at 1:1, and the loop polls and clears
`TMR2IF`. A period register is what makes an exact 1 ms tick a matter of
choosing two numbers -- a prescale code and a period -- rather than something
software has to assemble; Datasheet References records which two and how they
divide. One caution for anyone re-deriving them: the datasheet *prose* is
incomplete on the TMR2 prescale field, which is a two-bit code selecting 1:1,
1:4, 1:16 or 1:64. The register table is the authority there, and the device
pack's `pic10f322.h` is the authority for register and CONFIG *names*.

**The watchdog is independent of the tick.** `WDTCON.WDTPS` selects the period
from the 31 kHz LFINTOSC, which does not derive from `FOSC` and shares no
prescaler with any timer, so the watchdog neither moves when the core clock
changes nor competes with the tick for a resource. The nominal period is
~256 ms, chosen to mirror the AVR Classic's 250 ms so that one margin argument
covers both families; an earlier ~32 ms selection left only about 1.4x over the
worst-case awake burst and was lengthened for exactly that reason. The de-rated
floor the choice is judged against is in Watchdog Pet-to-Pet Budget.

**Two integrity checks are stronger than the obvious version, deliberately.**

* `hw_output_state_intact()` compares the **complete** implemented `TRISA`
  state, not merely the pins the caller requires, **and** compares the full
  `LATA` output latch against the expected mask. Each half covers what the
  other misses: a subset direction check cannot see a direction flip on a
  spare output -- `cd4053_simple`'s RA2 would float invisibly -- and a
  latch-only check cannot see a direction flip at all, because `LATA` still
  reads back the correct value when the pin has been turned into an input.
* The pull-up check covers both halves of a two-part enable. A weak pull-up
  needs the per-pin `WPUA` latch **and** the global, active-low
  `OPTION_REG.nWPUEN`; an upset of either silently floats the footswitch. The
  AVR analogue checks a single `PORTB` latch, because there is only one thing
  to check.

**What the per-tick sanity gate guards:** `OSCCON.IRCF`, `WDTCON.WDTPS`, `PR2`,
`T2CON`, `ANSELA` over the output pins, the `WPUA` latch, and
`OPTION_REG.nWPUEN`. `IRCF` is the only read/write field `OSCCON` implements on
this part, so checking it covers that register's whole timing-relevant state
rather than a chosen slice of it. The emitted CONFIG word is not reviewed by
eye -- it is read back out of the built HEX and compared against documented
intent by a build gate, because a wrong CONFIG bit is invisible to every other
test and would only bite on silicon.

**What still has to be validated, and what does not.** Because
`src/bypass_pure.c` is compiled unchanged into this image, the host, golden
model and formal suites that establish the algorithm establish it here too; no
PIC-specific argument about the debounce or the state machine is required, and
none is made. What remains is the shell, and it is validated on its own terms:
the CONFIG word against the built HEX, register-level simulation and fault
injection, built-HEX/model lock-step, target-I/O timing, static analysis and
MISRA, a soak lane and mutation testing. `test/README.md` owns what each layer
asserts and how to run it. The AVR Classic shell remains the reference
implementation with the longest validation history.

[[pic10f320-architecture]]
=== PIC10F320: the constrained target

The PIC10F320 is the same silicon family as the PIC10F322, pin-compatible in
this design, with the same peripherals and the same CONFIG posture -- and
**256 words of program flash, exactly half**. Everything below follows from that
one number.

**The modular architecture does not fit, and that is measured rather
than assumed.** Measured 2026-06-26 at source commit `0b44c0d` with free-tier
XC8 V3.10 and PIC10-12Fxxx DFP V1.9.189, the modular firmware for this part
built at 356, 386 and
381 words for the simple, mute and relay variants -- roughly 100 words over 256
in every case, and hard link failures rather than near misses. Three
source-level reductions were then priced rather than estimated. Packed enums
saved nothing, because the optimizer already emitted identical code and packing
shrank only the unconstrained RAM. Force-inlining the core saved nothing,
because the free tier silently ignores `always_inline` and left
`debounce_step()` a standalone function. Rewriting `debounce_step()` to fill a
pointed-to result saved twelve words and was the only robustness-neutral win,
which is not remotely enough. Bit-packing the context and result structs saved
the most at 47 words, still left the image 53 words over, and was refused on
correctness grounds that are stated in Failsafe Mechanisms rather than here,
because they apply to every target. The two best ideas did not even compose:
stacking them was *larger* than bit-packing alone, which is the signature of a
floor. So `src/bypass_mcu_pic10f320.c` is a single self-contained file: the
saturating integrator and the state machine are written directly in `main()`,
debounce initialization directly in `init()`, and the three output variants are
source-local static functions selected by `#if defined(OUTPUT_*)`. It links
neither `src/bypass_pure.c` nor the modular output drivers.

**The seam, stated plainly.** Inlining by hand creates two expressions of the
same algorithm that no compiler is keeping in step. On every other target that
seam does not exist, because there is one expression and it is compiled
straight into the image. This is the one trust assumption the PIC10F320
carries that no other target does. It is heavily mitigated, but it is
mitigated rather than eliminated, and this project would rather say so than
imply a parity it has not earned.

**What closes the gap, and how far.** The host-equivalence and real-HEX
lock-step lanes compare this firmware against `src/bypass_pure.c` **itself** --
the same file every modular target compiles into its shipping image, not a
vendored copy -- with the thresholds taken from `src/bypass_config.h` through
a host shim. A core change this firmware does not mirror therefore produces a
divergence that fails the suite, which makes the manual sync enforced rather
than merely documented. Orthogonal evidence covers actuation sequencing, fault
handling, source coverage, emitted bytes, CONFIG, return-stack depth, static
analysis, soak and mutation. What none of that does is make the architecture
identical: a behavioural equivalence argument, however thorough, is a
different kind of statement from "the verified code is the shipped code". The
honest summary is that this target's qualification design reaches for the same
standard by a different and more elaborate route.

**The shared surface, because a manual sync needs a checklist.** A core change
does not propagate here the way it does everywhere else, so the surface that
has to be mirrored by hand is worth naming in full. It is small, finite and
auditable:

|===
| Item | Core or driver source | PIC10F320 firmware

| Press threshold
| `PRESSED_THRESH` in `src/bypass_config.h`
| its own `#define`

| Release / lock-out threshold
| `RELEASE_THRESH` in `src/bypass_config.h`
| its own `#define`

| Saturating integrator
| `debounce_integrate()` in `src/bypass_pure.c`
| written directly in the `main()` loop

| State machine
| `debounce_step()` in `src/bypass_pure.c`
| a `switch` written directly in `main()`

| Power-on initialization
| `debounce_init_context()` in `src/bypass_pure.c`
| written directly in `init()`

| Output stages
| the three `src/bypass_output_*.c` drivers
| source-local static functions under `#if defined(OUTPUT_*)`

| Analog-switch polarity
| the unified drive in both CD4053 drivers
| source-local high/low helpers
|===

The pin map and the CONFIG word are PIC-local and shared with nothing. Read the
table as the checklist for what to edit, not as the mechanism that catches you
forgetting -- the equivalence lane is that mechanism, and it does not reach two
of these rows. The output-stage rows are covered instead by the actuation lane,
and a change that touches only the *defensive* layer is compared against the
PIC10F322 shell by no automatic gate at all, which is why the omission below is
recorded rather than merely known.

**The hardware return stack, and why it gets its own gate.** This is the one
resource bound on this part that no other gate observes, and three facts make
it a design concern rather than a build detail. First, it is not the AVR's
question: `test-stack-bound` bounds a *data* stack in bytes, and the PIC14 core
has none -- XC8 overlays locals into static, non-reentrant storage -- so what
is bounded here is the fixed eight-level hardware **return** stack, with the
budget read from the device pack rather than hardcoded. Second, "it is inlined,
so it cannot recurse" would have been the wrong answer: the debounce logic is
inlined, but the output stages are not, and every variant reaches one from
`init()`. Third, and decisively, the compiler cannot be the witness. XC8's own
per-function estimate was once **3** on a real relay image whose emitted
instruction stream contained a verified **4**-deep chain of `fcall`s, and its
overflow check is only a warning -- a deliberately ten-deep chain compiles to
`warning: (1393) possible hardware stack overflow detected` and `xc8-cc` still
exits 0 and writes a HEX. Overflow is undetectable at runtime on this core:
there is no `STKPTR`, no `TOSL`/`TOSH`, no `STKOVF` bit in `PCON` and no CONFIG
`STVREN`, so the stack silently wraps and a return goes to the wrong address.
The project therefore uses **two independent witnesses** -- one over the emitted
assembly, one reconstructing control flow from the shipped HEX -- and a
disagreement between them is itself the finding. The HEX witness fails closed at
its own boundary rather than guessing: reserved words, `RETFIE`, computed `PCL`
writes, data-dependent writes through `INDF` and any path that could enable
`GIE` are rejected rather than modelled. One limit belongs with the design
rather than the mechanics: running the oracle inside every build proves what
the recipe produced, not that the file was not modified afterwards. Release
provenance and reproduction are separate evidence.

**One recorded omission.** The exact-`TRISA` direction check was ported here
because it cost one word per variant; the general output-**latch** match was
not, because in every formulation that preserves its meaning it overruns 256
words on two of the three variants. Taking it on `cd4053_simple` alone was
considered and rejected, because a partial version of a general defence makes
the same class of fault depend on the selected output stage. What the relay
variant does buy, within its 256 words, is exactly the two coil latch bits --
an energized coil has a hardware-energy and relay-position consequence that a
wrong LED or analog-control level does not, so it escalates through the
forced-reset path like any other fault (Failsafe Mechanisms). The residual gap
is therefore precise: a wrong LED or analog signal path can persist until the
next accepted press. The context checksum is likewise absent here for the same
capacity reason, with the range check still in force.

**What this package does not establish,** stated so nobody has to infer it.
The seam remains a seam: everything above is a behavioural assurance argument,
and however thorough it is, it is a different kind of statement from "the
verified code is the shipped code". The expected-image gate is not universal
compiler reproducibility -- it holds the three emitted images against a
committed, reviewed baseline from the pinned toolchain, so byte drift fails
until an intentional rebaseline, but it says nothing about what a different XC8
version or environment would emit. The general output-latch check is absent,
as above. And the hardware-bench properties -- watchdog and brown-out timing,
absolute tick period, real-silicon pulse widths -- are simulated rather than
proven, a limit this target shares with the PIC10F322 because both are
validated in the same simulator; `test/README.md` carries the full list.

**Target-selection consequence.** Prefer another part whenever the choice of MCU
is yours: the AVR Classic parts, the ATtiny202 and the PIC10F322 all compile
the verified core directly, and the PIC10F322 is pin-compatible with this part
in this design, has double the flash and carries the full defensive layer. Use
the PIC10F320 when it is a hard requirement -- cost, existing inventory, or an
established board. It is release-supported, with published prebuilt images
beginning with `v0.9.6`.

**Where the rest of it lives.** `test/README.md` owns the current lane
inventory -- Make target, substrate, and the property each layer establishes.
Measured results and qualification status belong to the retained release
record under `release/<version>/`, which identifies the qualified source
commit; this document does not restate them. Exact check counts and fixture
inventories belong to the executable tests themselves, so no document can go
stale against the suite. Standing expected-image digests are
`test/pic10f320/expected_images.sha256`.

**Where the firmware came from.** This target was merged in from a separate
repository by a non-squashed `git subtree` import, so its full development
history is reachable here and its six predecessor signed release tags are
preserved under a `pic10f320/` namespace. Two consequences are worth knowing
before doing archaeology on it. The import is a merge commit, so a plain
`git log --follow` stops there -- `-m` is needed to descend into the second
parent. And the predecessor project's own binaries were deliberately not
copied in, because their version numbers collide with this project's line;
unified prebuilt PIC10F320 images begin at `v0.9.6`. Making a single-command
`--follow` work would have meant rewriting the imported commits, which
sacrifices their object identity and invalidates those signed tags. That trade
was declined.

[[pic12f675-architecture]]
=== PIC12F675: the classic mid-range shell

The PIC12F675 is a modular target -- `src/bypass_mcu_pic12f675.c` and
`src/bypass_pins_pic12f675.h` on top of the shared output drivers, compiling
and linking the same `src/bypass_pure.c` -- and its shell shares no register
code with the PIC10F322's. That it could be modular was established before the
shell was written rather than discovered afterwards: measured 2026-08-05 on
`main` at `0cfc72e`, with the pinned free-tier XC8 and device pack, a spike
shell carrying the complete defensive layer built the three variants at 494,
520 and 523 of the part's 1024 words. Roughly half the flash was spare, against
39 words spare on the PIC10F322, so this part never faced the question
<<pic10f320-architecture>> had to answer. Those are historical spike figures,
not a measurement of any current image; what each shipped image occupies is
release evidence. Six differences drive the design.

**There is no output latch.** `GPIO` reads the **physical pin levels**, not the
last value written, so the read-modify-write idiom that is safe against `LATA`
becomes a read-modify-write on the pins: a loaded output, or one still
slewing, can read back a level other than the one written, and the write-back
then corrupts other bits of the same port. Every level change therefore goes
to an SRAM shadow, and the whole shadow is written to `GPIO`. That cuts three
ways, and all three belong in the design record:

* **It makes the integrity check stronger than the PIC10F322's.** With a shadow
  it becomes possible to compare intent against reality as well: the shadow
  against the expected mask, **and** the physical `GPIO` bits against the
  shadow. The second comparison catches a driver, pin or bus fault where the
  port does not follow the latch -- a class of fault the PIC10F322 cannot see
  at all.
* **It puts an SRAM byte in the safety path,** which is exactly what this
  project's upset threat model says can flip. The shadow guards itself: an
  upset diverges it from the expected mask or from the port, and either way
  the gate fires. It is a guarded location and a fault-injection case in its
  own right.
* **It imports a board requirement.** Reading the outputs back makes the guard
  depend on the output pins' **input** thresholds, and those are not uniform:
  GP2 is the only output in this design whose input buffer is a Schmitt
  trigger rather than TTL. A GP2 held high in a checked state must read back
  above the Schmitt threshold or the gate fires permanently. Both documented
  board options clear it by a wide margin; the PIC12F675 pinout section above
  states the requirement and which variant it binds.

**The clock is fixed, and its calibration lives in flash.** There is no
`OSCCON` and no runtime frequency selection: the oscillator is 4 MHz, trimmed
by `OSCCAL`, whose value is factory-programmed as a `RETLW` instruction in the
**last program word** and loaded by the compiler's startup code. Three things
follow. The oscillator guard cannot be a compile-time constant, so the shell
snapshots `OSCCAL` at the end of initialization and compares it every tick.
An erase that does not preserve that word leaves a device whose every delay
and tick cadence is wrong -- which is why it is a gated part of the operator
procedure in `FLASHING.md` rather than a footnote. And no unmodified image
runs in a simulator at all: startup calls the missing word, runs off the end
of flash and watchdog-resets in a loop. The simulation lanes therefore run a
**derived** image with the calibration word injected, and the derivation
boundary is a hard rule: the injected image is a build artifact that never
becomes a shipping or programming image. A release therefore carries two
distinct PIC12F675 artifacts -- the shipped HEX and the derived one the
simulator lanes drive -- each hashed in its own right, so no simulator
convenience can reach a device.

**One prescaler, so the tick is constructed rather than configured.**
`OPTION_REG.PSA` assigns the part's single prescaler to TMR0 **or** to the
watchdog, never both, and no timer here has a period register. Giving the
prescaler to the watchdog is what buys a watchdog period long enough to
outlast a blocking coil pulse; TMR0 is then unprescaled at F_OSC/4, and four
256 us rollovers counted in software make one tick. The tick is therefore
1.024 ms rather than 1 ms. The pure core counts samples and is unaffected, but
every wall-time figure derived from the tick moves by 2.4% -- see Caveats and
Limitations and Asymmetric Debounce Timing, and note that the soak harness
derives its holds **through** the tick period rather than assuming one. The
blocking actuation does not scale with the tick: a coil pulse and a mute
settle are wall-clock waits in the shared drivers, so a block of `B` ms costs
`B` ms of tick accumulation whatever the tick period is.

**The analog hazard surface is three paths wide, not one.** Where the
PIC10F322's only analog encroachment is `ANSELA`, this part has three, and all
three are cleared in initialization and guarded per tick:

* `CMCON` -- out of reset the comparator mode makes GP0 and GP1 analog
  inputs, and an analog input reads back 0 whatever the driver is doing.
  `TRISIO` still owns direction, so what the reset state breaks is **readback**,
  which is precisely what the port-follows-shadow comparison exists to catch.
  Comparator output modes can additionally take GP2.
* `ANSEL` -- covers GP0, GP1, GP2 and the parked GP4. Its bit for GP4 is
  `ANS3`, not bit 4, so the GPIO output mask cannot be reused for this
  comparison.
* `ADCON0.ADON` -- the same class of hazard, and guarded for the same reason.

**One register carries three safety-relevant fields.** `OPTION_REG` holds the
watchdog period (`PSA`/`PS`), the tick clock source (`T0CS`) and the global
pull-up enable (`nGPPU`). It is therefore compared exactly rather than field
by field. This cuts both ways and is worth naming in review: on the PIC10F322
those three concerns are three independent registers, so a single-bit upset
here is more likely to land on something safety-relevant, and one exact
comparison covers all of it.

**The pin map is not the PIC10F32x map renamed.** `WPU` implements no bit for
GP3, so the input-only pin has no internal weak pull-up and the footswitch
cannot live there the way it does on the PIC10F322; it lives on GP5, the one
bidirectional pin with no analog function. GP4 is a parked output driven low
and inside the guarded mask rather than an unconnected spare. The complete map
and the board requirements it imposes are in the PIC12F675 pinout section
above.

One near-neighbour was considered and not taken. The PIC12F629 is the same die
minus the ADC: same 1024 words, same eight-level stack, CONFIG at the same
address, and `GPIO`, `TRISIO`, `WPU`, `OPTION_REG`, `CMCON` and `OSCCAL` at the
same addresses, with `ANSEL` and `ADCON0` the only registers it does not have.
gpsim supports it, and a family shell guarding those two writes and their two
sanity checks behind one conditional would cover both parts. The repository
builds exactly one of them, so the shell is named for that part rather than for
a family; generalizing it is a decision available later, not a debt.


== AVR Classic Program Flow

=== Functional Description

Define two program states: PRESS_DEBOUNCE_WAIT, RELEASE_DEBOUNCE_WAIT
Define two effect-circuit states: ENGAGED, BYPASS
Define constants (see "Asymmetric Debounce Timing" above for rationale)
    * RELEASE_THRESH = 25
    * PRESSED_THRESH = 8

The core mechanism is a saturating integrator: a counter that
increments by one per sample when the footswitch reads closed,
and decrements by one per sample when it reads open, bounded
between 0 and RELEASE_THRESH. A simple debounce timer resets on any
noise sample; the integrator tolerates noise, requiring only that
the majority of samples over a window indicate the intended state. A
single pulse that cannot cover PRESSED_THRESH sample instants cannot reach the
threshold. Starting from counter zero, and measuring low duration at the MCU
digital input, the stated +/-10% clock tolerance guarantees that any pulse
shorter than about 6.36ms is too short; longer pulses can register depending on
sample phase, and noncontiguous lows can accumulate if high samples do not
cancel them. A real press, even through moderate contact bounce or EMI,
accumulates reliably because each
clean low sample contributes persistently.

The state machine has two states. In PRESS_DEBOUNCE_WAIT, the
integrator climbs while the switch is held and falls while released.
When it reaches PRESSED_THRESH, the effect is toggled immediately
and the counter is loaded with RELEASE_THRESH, arming the lockout.
In RELEASE_DEBOUNCE_WAIT, the integrator can only drain (the switch
is being released). Only when it reaches zero does the machine
re-arm for the next press. This lockout prevents switch bounce on
release from generating a second event, and prevents a held switch
from re-triggering.

The thresholds are asymmetric by design. `PRESSED_THRESH` is eight accepted low
samples (often given the nominal shorthand "8ms", but not a fixed physical
duration) and is kept low for fast response. Under clean input, edge-to-toggle
latency is about 7 to less than 8 tick periods depending on sample phase.
`RELEASE_THRESH` is 25 accepted high samples, providing robust lockout against
release bounce while still allowing fast repeated taps. The conservative
algorithmic qualification budget is 8 + 25 = 33 sample updates; at a nominal
1ms tick it is labeled 33ms, but it is not an exact physical minimum. See
"Asymmetric Debounce Timing" for the phase and oscillator bounds.

=== State Machine

Saturating integrator (one update per nominal 1ms sample, runs in both states):

  if footswitch pin low  (switch closed):  if counter < RELEASE_THRESH: counter++
  if footswitch pin high (switch open):    if counter > 0             : counter--



.Table Program state machine (evaluated after each sample update)
|===
| Current State        | Condition                   | Effect action                                    | Next State

| PRESS_DEBOUNCE_WAIT  | counter >= PRESSED_THRESH   | Toggle engaged/bypass; counter = RELEASE_THRESH  | RELEASE_DEBOUNCE_WAIT
| PRESS_DEBOUNCE_WAIT  | counter <  PRESSED_THRESH   | (none)                                           | PRESS_DEBOUNCE_WAIT
| RELEASE_DEBOUNCE_WAIT| counter == 0                | (none)                                           | PRESS_DEBOUNCE_WAIT
| RELEASE_DEBOUNCE_WAIT| counter >  0                | (none)                                           | RELEASE_DEBOUNCE_WAIT
|===



=== Timing Diagram

Diagram 1: Typical Clean Case

Eight accepted low samples span seven intervals; the physical edge can occur
anywhere in the one interval before low sample 1. `T` is the actual tick period.

   low sample number:       1   2   3   4   5   6   7      8
   elapsed from sample 1:  0T  1T  2T  3T  4T  5T  6T     7T
   counter after sample:    1   2   3   4   5   6   7  [8 -> 25]
                                                            ^ toggle fires;
                                                              lockout loads

   clean physical edge-to-toggle latency: approximately 7T to less than 8T
   nominal T=1ms:                            approximately 7ms to less than 8ms
   T with +/-10% frequency tolerance:        approximately 6.36ms to less than 8.89ms

These are ideal sample-qualification bounds; physical edge-to-output latency
also includes the small, sub-tick instruction path that processes the final
sample and updates the output.

After an immediate release, 25 accepted high samples drain the lockout. Those
25 sample instants span 24 intervals after the first high sample:

   high sample number:       1   2   3  ... 23  24  25
   counter after sample:    24  23  22  ...  2   1   0
                                                     ^ re-arm

The commonly quoted 8ms press and 33ms press/release figures are nominal
sample-count labels and conservative scheduling budgets, not fixed physical
durations.
