## A3 — BOD/BOR failsafe list omits two of six release parts (safety-relevant)

**Status:** DONE `7f9986f`
**Priority:** HIGH — this is the one item with a real-world safety edge
**File:** `DESIGN_DOCUMENTATION.adoc`, *Failsafe Mechanisms*, the `[horizontal]`
definition list (~lines 196–207)

### Evidence

The list currently has exactly two entries:

```
AVR Classic (ATtiny13a/45/85):: 4.3v BOD fuse -- enforces the >4v
  floor the 5v relay coil / MOSFET peripherals require.
PIC10F322:: BOR is enabled at the highest available trip
  (`BORV=HI`), but the PIC10F322's trip points are only ~2.4v (LO) /
  ~2.7v (HI). ...
```

Both **ATtiny202 and PIC10F320 are missing**, and both are release-supported
parts in the 18-image v0.9.6 product set. The section's own framing — "the
BOD/BOR floor is MCU-family-specific and not every supported part can enforce
the >4v peripheral-safe threshold" — promises per-part coverage it doesn't
deliver.

**PIC10F320 (the safety-relevant omission).** `src/bypass_mcu_pic10f320.c` sets
`#pragma config BOREN = ON`, `LPBOR = OFF`, `BORV = HI` — identical to the
PIC10F322. Same silicon family, same ~2.4 V (LO) / ~2.7 V (HI) trip points. It
therefore carries **exactly the same caveat**: it cannot enforce a >4 V floor in
firmware, so a PIC10F320 build driving a 5 V relay coil or MOSFET must guarantee
the peripheral-safe supply in hardware. The 322 says this; the 320 doesn't.

**ATtiny202 (the omission that undersells us).** `XT_FUSE_BODCFG ?= 0xE5`
(`Makefile`). Decoded: `LVL = (0xE5 >> 5) & 7 = 7`, `SAMPFREQ = 0`,
`ACTIVE = 1 (ENABLED)`, `SLEEP = 1 (ENABLED)`. Cross-checked against the pinned
device pack, `third_party/attiny_dfp/include/avr/iotn202.h:842-845`:

```c
LVL_BODLEVEL0_gc = (0x00<<5),  /* 1.8 V */
LVL_BODLEVEL2_gc = (0x02<<5),  /* 2.6 V */
LVL_BODLEVEL7_gc = (0x07<<5)   /* 4.2 V */
```

So the ATtiny202 runs BODLEVEL7 = **4.2 V, BOD active in both run and sleep** —
it *does* enforce the >4 V peripheral-safe floor, and it is the AVR-XT analogue
of the classic 4.3 V BOD. That is good news currently going unstated.

### Fix

Add two entries to the same `[horizontal]` list, matching the existing style:

- `ATtiny202 (AVR-XT)::` — BODCFG `LVL=BODLEVEL7` (~4.2 V), ACTIVE and SLEEP
  both enabled; enforces the >4 V floor, the AVR-XT analogue of the classic
  4.3 V BOD.
- `PIC10F320::` — same silicon family and same `BOREN=ON`/`BORV=HI`
  configuration as the PIC10F322, therefore the **same ~2.7 V ceiling and the
  same hardware-design caveat**.

Keep the PIC10F320 wording as explicit as the 322's. Do not merge the two PIC
entries into one line unless the merged line names both parts — per the
`pic-naming-322-vs-32x` convention, a note that applies to both parts should say
so rather than silently generalising from "322".

### Resolution (2026-07-29)

Both fuse claims re-verified from primary sources before writing any
safety-relevant prose. The list now has four entries, one per MCU family.

**ATtiny202 — decode confirmed against the pinned pack, not the datasheet.**
`Makefile:1782` sets `XT_FUSE_BODCFG ?= 0xE5`. The bit positions come from
`third_party/attiny_dfp/include/avr/iotn202.h:3168-3183`:

```
FUSE_LVL_gm  0xE0, FUSE_LVL_gp  5
FUSE_ACTIVE_gm 0x0C, FUSE_ACTIVE_gp 2
FUSE_SLEEP_gm  0x03, FUSE_SLEEP_gp  0
FUSE_SAMPFREQ_bm 0x10
```

0xE5 = `1110_0101` decodes to LVL=7, SAMPFREQ=0, ACTIVE=1, SLEEP=1. Against
`LVL_enum` (`:839-844`) and `ACTIVE_enum` / `SLEEP_enum`: **BODLEVEL7 = 4.2 V,
BOD ENABLED in active mode, ENABLED in sleep.** BODLEVEL7 is one of only three
enumerated levels (1.8 / 2.6 / 4.2 V), so it is characterised, not reserved.

> **Trap for anyone re-checking this:** `iotn202.h` has *two* BOD level enums.
> `BOD_LVL_enum` (`:310-315`) shifts by **0** — that is the runtime `BOD.CTRLB`
> register. The fuse enum `LVL_enum` (`:839-844`) shifts by **5**. Decoding the
> BODCFG *fuse* byte with the register enum gives a wrong answer. Use
> `FUSE_LVL_gp = 5`.

**PIC10F320 — confirmed identical to the 322.** `src/bypass_mcu_pic10f320.c:108,114,115`
sets `BOREN=ON`, `LPBOR=OFF`, `BORV=HI`; `src/bypass_mcu_pic10f322.c:53,59,60`
sets exactly the same three. Same silicon family, same ~2.4 V / ~2.7 V trips,
same inability to enforce a >4 V floor.

Wording choices, per the constraint above: the two PIC parts are kept as
**separate entries**, and the shared hardware-design caveat sentence in the
PIC10F322 entry was changed from "A **PIC build** that drives >4v peripherals"
to "A build on **either PIC part** that drives >4v peripherals" so the shared
advice names both parts instead of generalising from "322".

Swept: this `[horizontal]` list is the only per-part BOD/BOR coverage claim in
the live tree. Other hits (`test/README.md:440-442` gpsim analog-BOR gap,
`docs/phase2_pic_shell.md:85` config-bit list, `TODO.md` items) are correctly
scoped already. AsciiDoc structure unchanged — same `[horizontal]` block, two
more `::` entries; `asciidoctor` is not installed here so no render check was
possible, but no block delimiters were touched.

### Follow-on found while verifying (not fixed — firmware)

`src/bypass_mcu_pic10f322.c:32-36` carries an explicit "BOR note" comment
explaining the ~2.4/~2.7 V limitation. **`src/bypass_mcu_pic10f320.c` has the

## E6 — The stack high-water-mark gate's diagnostic overstates free SRAM by 4 bytes

**Status:** DONE — edit applied to working tree, awaiting user commit
**Priority:** MEDIUM
**File:** `test/avr/test_sim.c:1955-2004`
**Found:** while verifying E3

### Evidence

Both the function comment and the failure message say the margin is measured
against BSS:

```
// Asserts adequate margin between the stack bottom and the BSS region.
...
CHECK(margin_bytes >= 8u,
      "stack leaves only %u bytes between deepest SP (0x%03X) and BSS; "
      "expected >=8 bytes margin", ...)
```

The code measures something else:

```
const uint32_t sram_bot = 0x60u;         // first SRAM byte on AVR (data space)
...
uint32_t margin_bytes = (deepest_sp > sram_bot) ? (deepest_sp - sram_bot) : 0u;
```

`0x60` is the **bottom** of SRAM. The 4 bytes of static data (`timer_isr_called_`
and `ctx_`) sit at exactly that address, *inside* the span being measured. So
`margin_bytes` is the gap to the bottom of BSS, not to the top of it, and it
overstates the genuinely free bytes by the size of BSS — 4 today.

Measured (`make test-sim`): reported margin 33 B on relay/mute, 35 B on cd4053;
genuinely free 29 B and 31 B.

### Why this matters

The error is in the optimistic direction, in a gate. At the 8-byte floor the
stack may reach within **4** free bytes of BSS while the message announces 8.
Anyone reading a near-failure — the exact moment this diagnostic exists for —
is told the situation is twice as comfortable as it is. Today's 33 B is nowhere
near the floor, so this is a latent reporting defect, not a live one.

It also means the doc and the gate print different numbers for the same thing.
E3 handled that by reconciling both in prose; fixing this would let them simply
agree.

### Two fixes, user's call

**(a) Correct the words, leave the arithmetic alone.** Change "BSS" to "the
first SRAM byte" in the comment and the message, and say the span includes
static data. Zero behavioural change — no gate can flip. This is the minimal
change and matches the standing preference to take the small fix now.

**(b) Correct the arithmetic to match the words.** Measure down to the top of
BSS so the 8-byte floor means 8 genuinely free bytes. The test already resolves
ELF symbols (`g_addr_program_state`), so `_end`/`__bss_end` is reachable the
same way. Worst-case margin would read 29 B instead of 33 B — still 21 B above
the floor, so **this does not flip any current result**, but it does tighten the
gate by 4 bytes and should be run against all three variants before landing.

Recommendation: **(b)**, with (a) as the fallback if the symbol lookup turns out
to be awkward. The measurement is cheap to correct, the gate is the project's
only runtime SRAM guard, and (b) makes the doc, the message and the arithmetic
all state the same number instead of three reconciled ones.

### Verify (either fix)

`make test-sim` — expect the same 10060 / 9862 / 9868 checks, 0 failures, with
the printed margin becoming 29/31 under (b) and unchanged under (a).

### Resolution (2026-07-29) — user chose (b)

The reference point is read from the firmware ELF, not assumed. simavr already
exposes the linker's symbols (`elf_read_firmware` publishes 44 of them for
`bypass_relay.elf`, `__bss_end` and `_end` among them — confirmed with a
standalone probe before writing any code, rather than hoping). `sim_reset_raw()`
now resolves `g_addr_bss_end`, preferring `__bss_end` and keeping `_end` only as
a fallback, since `_end` also tracks the heap base on parts that have one.

`margin_bytes` is now measured from `deepest_sp` down to that address instead of
to `0x60`. Reading it out of the ELF rather than computing it from the known
globals is the point: **a static variable added tomorrow tightens the gate by
itself**, where `bss_end = ctx_ + 4` would have gone quietly stale.

Fails closed, per the project's discipline: if `__bss_end` cannot be resolved the
test reports it and fails. It does not fall back to `sram_bot`, which would have
silently restored the 4-byte-loose behaviour this item exists to remove.

The printed line now names the static region so the arithmetic is checkable
without reading the source:

```
stack HWM: deepest SP=0x081, used=31 B, margin=29 B free (SRAM 0x060-0x09F, 64 B total; static 0x060-0x063, 4 B)
```

Verified:

- `make test-sim` (ATtiny13a) → **10061 / 9863 / 9869 checks, 0 failures**;
  margins now **29 B** (relay, mute) and **31 B** (cd4053), matching the design
  doc exactly instead of differing from it by 4. The +1 check per variant is the
  new fail-closed guard.
- `make test-sim-secondary` (ATtiny45, ATtiny85, all variants) → six binaries,
  0 failures; margins 221–479 B, static region correctly 4 B on every one
- **Fail-closed path exercised, not assumed:** stripped `__bss_end` and `_end`
  from a copy of `bypass_relay.elf` with `avr-objcopy` and pointed a test build
  at it → `FAIL ... could not resolve __bss_end (got 0x000; need ELF symbols)`,
  exit 1. A control run of the *same reduced-iteration build* against the
  unstripped ELF isolates it: 2 failures there (artifacts of the shortened
  iteration counts) vs 3 with the strip, so the guard accounts for exactly one.

`DESIGN_DOCUMENTATION.adoc` follows: E3 had to spend three sentences reconciling
33 with 29, and that paragraph now just states 29 and says where the reference
point comes from. Fixing the measurement made the documentation shorter, which
