## Purpose

Release v0.9.9 added release-supported PIC12F675 firmware and substantially
expanded the Makefile, simulator, mutation, qualification, programming, release,
and documentation machinery. This pass scrutinizes that work and the project as
a whole against the project's correctness, robustness, reliability, and
reference-quality goals.

The review found no nominal-path PIC12F675 firmware defect. Its shell,
calibration-image separation, CONFIG value, stack bounds, GPIO-shadow design,
target-I/O sequencing, and 1.024 ms timing model are internally coherent. The
highest-priority findings are instead in release-byte provenance, the guarded
programming transaction, and fault-path behavior.

This is a TODO, not an implementation plan fixed in stone. Discuss each item
before changing code. Prefer the smallest change that closes the stated failure
mode and proves it with a focused regression.

## P1 - Bind release flashing to signed release bytes

**Status:** DONE (pending owner commit)
**Priority:** HIGH
**Scope:** `release/README.md`, `scripts/release-documentation.sh`, `Makefile`,
programming regressions

### Finding

The published PIC12F675 release procedure checks that `HEAD` equals the selected
tag and that the worktree is clean only before the read-only baseline capture
(`release/README.md:327-346`). `pic12f675-program` later rebuilds from the live
tree (`Makefile:6861-6875`), checks calibration and CONFIG, and binds every
subsequent operation to an internally consistent private snapshot
(`Makefile:6893-6918`, `Makefile:6960-6965`). It never proves that the snapshot's
digest is the digest listed for that variant in the signed release
`SHA256SUMS`.

The current transaction is therefore strongly bound to *some fresh build*, but
not necessarily to the released bytes. A source change after the initial check,
an unintended `PIC_CC`/`PIC_DFP` selection, or compiler output that differs from
the qualified release can be programmed while all current transaction checks
report PASS. That contradicts the release provenance promise even when the
resulting firmware is otherwise valid.

### Recommended direction

Create an explicit release-flashing path that knows the selected release tag and
variant. Before hardware is reachable, verify the pinned detached signature,
read the selected image digest from that release's `SHA256SUMS`, and require the
private fresh-build snapshot to match it exactly. Keep the existing
snapshot-immunity checks; signed-release binding is an additional outer
contract, not a replacement.

Recheck the tag/source identity immediately before the private build, or build
from an immutable committed-source view. Account deliberately for the baseline
and result paths created by the published transaction rather than weakening the
clean-tree check globally.

If development/bench programming must remain possible for unreleased source,
make that a distinct, explicit mode or goal. It must not be possible to mistake
an unqualified development build for release flashing.

### Acceptance criteria

1. The correct tagged source and pinned toolchain produce a snapshot whose hash
   matches the signed release record and may reach the fake writer.
2. A tracked source mutation between preflight and program is rejected before
   writer invocation.
3. A compiler that emits a valid but byte-different image is rejected before
   writer invocation.
4. A mismatched release tag, variant, checksum entry, checksum signature, or
   release image set is rejected before writer invocation.
5. The writer still receives exactly the private read-only snapshot checked by
   calibration, CONFIG, and digest gates.
6. Release instructions generated into future manifests exercise the same path
   as the regression tests.

### Resolution

Added `pic12f675-release-program` as a distinct signed-release path while keeping
`pic12f675-program` explicitly available for development and bench builds. The
release path requires an exact clean annotated-tag checkout, verifies the pinned
tag and detached checksum signatures, validates the complete canonical release
image set, and requires the private selected snapshot to match its signed digest
before any hardware command. Baseline, result, and transient paths must remain
outside the worktree so the source checks stay exact.

The fake-programmer regression now covers matching signed bytes, tracked-source
mutation, valid byte drift, tag/signature failures, worktree-local evidence, and
the exact checked snapshot reaching the writer. Release-image regressions cover
variant, checksum-entry, annotated-tag identity, and complete-set failures. The
generated future-manifest transaction invokes the same release target. The
immutable `v0.9.9` tag predates this new target; the protection applies to release
tags that contain it.

## P2 - Make the programming CONFIG gate immutable

**Status:** TODO
**Priority:** HIGH
**Scope:** `Makefile`, `test/pic/test_config_pic12f675.c`,
`test/pic/test_config_pic_core.h`, `test/test_pic_build.sh`

### Finding

The programming target depends on `test/pic/test_config_pic12f675`, an ignored
generated executable (`test/.gitignore:10-11`). Its file rule has no forced
rebuild and does not encode compiler identity in freshness
(`Makefile:5961-5962`). The programming recipe then accepts that executable on
exit status alone (`Makefile:6704-6706`, `Makefile:6911`).

A newer stale executable, or a zero-exit no-op placed at the ignored path, is
invisible to the published clean-tree check and can silently remove the only
pre-write design-intent check for FOSC, WDTE, PWRTE, MCLRE, BOREN, CP, CPD, and
BG. The calibration checker avoids this class by requiring an exact success
record; the CONFIG checker does not. Current fake-tool tests exercise a bad
CONFIG with a known-good checker and no-op/near-match calibration checkers, but
do not substitute a no-op CONFIG checker.

### Recommended direction

Do not consume a repository-adjacent ignored executable in the hardware path.
Compile the CONFIG checker unconditionally into the private programming
directory, or move the exact PIC12F675 CONFIG policy into an immutable tracked
oracle already used by the transaction. Require an exact image-bound success
record rather than exit status zero.

P1's signed-release digest check will independently protect release flashing,
but P2 remains necessary for development/bench programming and as defense in
depth against generating a dangerous image.

### Acceptance criteria

1. A pre-existing ignored `test/pic/test_config_pic12f675` cannot influence the
   programming transaction.
2. A zero-exit/no-output CONFIG checker cannot make the writer reachable.
3. A near-match or wrong-image success record cannot make the writer reachable.
4. Every safety-relevant CONFIG field and the exact expected word are checked
   against the private snapshot passed to the writer.
5. Bad FOSC, WDTE, MCLRE, BOREN, or BG fixtures fail before any hardware command.

## F1 - De-energize relay coils on detected faults

**Status:** NEEDS-USER
**Priority:** MEDIUM
**Scope:** modular MCU shells/output-driver interface, PIC/AVR fault tests,
mutation tests
**Existing durable TODO:** `TODO.md` `T25-relay-fault-abort`

### Finding

The PIC12F675 sanity gate can detect output corruption
(`src/bypass_mcu_pic12f675.c:567-580`), but `hw_force_wdt_reset()` only disables
interrupts and spins (`src/bypass_mcu_pic12f675.c:307-316`). An internally driven
relay coil intended for a 12 ms pulse can remain energized until watchdog reset,
potentially for approximately 160-480 ms over the characterized PIC12F675 range.
The same fault-handler shape exists in other modular shells.

PIC12F675 fault tests inject GP1/GP2 output states
(`test/pic/test_fault_pic12f675.cc:45-56`) but assert only eventual reset
(`test/pic/test_fault_pic_core.h:479-500`), not prompt electrical
de-energization.

### Recommended direction

Add a minimal relay-aware fault-abort operation that clears both coil outputs
before entering the watchdog wait. Preserve the watchdog reset as the recovery
backstop and do not introduce a normal-path transition or attempt to continue
after a critical fault. Define behavior for every output stage so the shell does
not acquire an unsafe variant-dependent call.

The repository owner must make the firmware source edit. Test work may proceed
under the owner's guidance.

### Acceptance criteria

1. One-coil and both-coil fault injections observe both physical coil outputs
   low within a reviewed instruction/cycle bound, before reset.
2. The watchdog reset still occurs exactly once and startup returns to BYPASS.
3. Mutations deleting either coil-clear operation are killed behaviorally.
4. Non-relay output variants preserve their existing fail-safe behavior.
5. Normal relay pulse width and sequencing remain byte-/behavior-qualified as
   intended after the source change.

## F2 - Detect in-range debounce-context corruption

**Status:** NEEDS-USER
**Priority:** MEDIUM
**Scope:** MCU shells, host/target fault injection, formal/model checks
**Existing durable TODO:** `TODO.md` `T3-ctx-complement`

### Finding

PIC12F675 rejects only context values above their legal ranges
(`src/bypass_mcu_pic12f675.c:571-578`). A single-bit flip can remain in range and
change behavior without tripping any guard. For example, an idle
`debounce_counter` can flip from 0 to 16; a released sample reduces it to 15
(`src/bypass_pure.c:24-29`), after which `debounce_step()` treats it as a
debounced press and toggles (`src/bypass_pure.c:46-63`). The resulting output
matches the new logical state, so the settled-output check does not catch it on
the next tick.

Target fault tests currently inject out-of-range values such as `0xFF`
(`test/pic/test_fault_pic_core.h:612-617`). They prove range-check recovery but
not the in-range SEU case in the project's threat model.

### Recommended direction

Evaluate complemented or otherwise redundant shell-owned storage for context
members, with every update and every tick checked consistently. Preserve the
pure core and account explicitly for AVR ISR/main ownership. If resource limits
force per-target differences, document and test those differences rather than
silently weakening one target.

The repository owner must make the firmware source edit.

### Acceptance criteria

1. Representative in-range single-bit flips of `program_state`, `effect_state`,
   and `debounce_counter` force recovery before an unintended output transition.
2. Every legitimate context update maintains the redundant representation.
3. AVR ISR/main interleavings cannot produce a false mismatch.
4. Mutation tests kill a missing update and a weakened comparison.
5. Flash, RAM, stack, MISRA, and target qualification remain within each MCU's
   reviewed budgets.

## P3 - Finalize interrupted programming transactions

**Status:** TODO
**Priority:** MEDIUM
**Scope:** `Makefile`, `test/pic/pic12f675_trim_evidence.py`, programming tests,
README/release instructions

### Finding

A handled signal exits through programming cleanup immediately
(`Makefile:6829-6847`). If it arrives during or after the writer, the mandatory
post-read and `result.json` creation are skipped. The regression explicitly
expects a retained `reservation.json` and writer log but no final result
(`test/test_pic_build.sh:2050-2065`). Other post-write infrastructure failures
can likewise leave only a PENDING reservation.

The reservation is useful forensic evidence, but the project provides no
read-only recovery/finalization command. Retrying with the same result path is
rejected, and starting a new baseline or write before resolving the existing
transaction risks losing the only reliable account of the device state.

### Recommended direction

Add a recovery/finalization goal that consumes the existing reservation,
performs no write, reads the currently attached device, and publishes a durable
PASS/FAIL resolution bound to the reserved baseline, image, reader, and writer
identity. Where practical, defer handled signals until a best-effort post-read
and FAIL record complete; power loss and `SIGKILL` will still require the
explicit recovery path.

Document physical-custody requirements and prohibit another write, reflash, or
new baseline until the PENDING transaction has been resolved.

### Acceptance criteria

1. A signal after simulated write consumption leaves a PENDING transaction that
   can be finalized without another write.
2. Recovery performs only version/read operations and never invokes writer
   arguments.
3. Matching post-read state produces a resolved record; trim, CONFIG, identity,
   or programmed-byte mismatch produces a durable FAIL record.
4. Reusing a reservation with a different baseline, image, part, variant,
   reader, or writer is rejected.
5. Re-running finalization cannot replace or contradict an existing final
   result.
6. User documentation gives an explicit safe response to PENDING evidence.

## R1 - Revalidate frozen publication assets before upload

**Status:** TODO
**Priority:** LOW
**Scope:** `.github/workflows/release.yml`, workflow regressions

### Finding

The release workflow verifies and copies publication assets into a frozen
directory (`.github/workflows/release.yml:327-332`), then executes all clean-runner
compiler/simulator gates before publication. The publish step uploads the HEX
files and metadata at lines 410-445, but re-hashes only `RENAME_IDENTITY.md`.

A post-freeze process error, cache/tool compromise, or storage corruption can
therefore alter a HEX, `SHA256SUMS`, signature, manifest, or qualification record
without making publication fail. A careful consumer will detect the resulting
mismatch, but the workflow should not publish an internally invalid bundle.

### Recommended direction

Record a complete frozen-bundle inventory and digest set when the snapshot is
created. Immediately before `gh release create`, verify every frozen file,
re-run detached-signature and image-checksum verification against that snapshot,
and reject added, missing, replaced, empty, or symlinked assets.

### Acceptance criteria

1. Mutating any frozen HEX or metadata asset after the test gates begin prevents
   publication.
2. Adding, removing, symlinking, or replacing an asset prevents publication.
3. Detached signature and image checksums are verified from the exact directory
   passed to `gh release create`.
4. `GH_TOKEN` remains exposed only to the final publication step.

## T1 - Correct the PIC12F675 watchdog evidence note

**Status:** TODO
**Priority:** LOW
**Scope:** `test/pic/test_fault_pic_core.h`, part adapters, target-result tests

### Finding

The shared fault harness always prints the PIC10F32x note saying gpsim uses
`WDTPS=0x08` and an approximately 1.057 s watchdog
(`test/pic/test_fault_pic_core.h:582-584`). The PIC12F675 uses

The fault verdict is unaffected because the common observation window is
deliberately generous. The defect is evidence accuracy.

### Recommended direction

Require each part adapter to supply its own watchdog-note string, as it already
supplies processor identity, program size, and expected check count. Refuse to
compile an adapter that omits the note.

### Acceptance criteria

1. PIC10F320/PIC10F322 output retains the gpsim 1.057 s modeling caveat.
2. PIC12F675 output states the approximately 288 ms simulated period and 160 ms
   silicon minimum without implying the simulator models RC spread.
3. A focused regression pins the correct note per part.

## T2 - Complete watchdog contracts

**Status:** TODO
**Priority:** LOW
**Scope:** owner-authored shell constants/assertions, fault harness, static-assert
tests, mutation tests
**Existing durable TODO:** `TODO.md` `T25-wdt-margin-assert`

### Finding

PIC12F675 correctly documents a 13.024 ms nominal worst normal pet-to-pet path
against a 160 ms watchdog floor (`src/bypass_mcu_pic12f675.c:409-416`), and the
host soak-timing contract pins `OPTION_REG_CONFIG=0x0C`. The inequality itself
is not enforced at compile time, unlike PIC10F320. A future tick, pulse, blocking
stage, or prescaler edit can erode the margin without failing the affected
firmware build.

The fault harness proves exactly one reset in its observation window but does
not require renewed main-loop liveness after each reset
(`test/pic/test_fault_pic_core.h:479-500`). The next case catches a dead recovery
indirectly, but the final injection has no successor
(`test/pic/test_fault_pic_core.h:612-617`).

### Recommended direction

Add per-shell, datasheet-derived compile-time watchdog floors and assert every
blocking variant's tick-plus-actuation bound against them. Keep de-rated minima,
not nominal periods, as the safety values.

After each expected fault reset, require the built image to reach the identified
main-loop watchdog-pet site again before the case passes. This is a test change;
the shell assertion changes are firmware source and must be made by the owner.

### Acceptance criteria

1. Raising a blocking delay beyond a target's de-rated watchdog floor fails that
   target/variant at compile time.
2. Mutating the watchdog floor or removing an assertion is caught by focused
   static-assert regressions.
3. Every injected fault proves reset followed by renewed loop-pet liveness.
4. The final fault case has the same post-reset guarantee as every earlier case.

## T3 - Keep metadata-only verification tool-independent

**Status:** TODO
**Priority:** LOW
**Scope:** `scripts/verify-release-qualification.sh`, Makefile introspection,
release-verifier tests

### Finding

`verify-release-qualification.sh` documents `make` as its only tool prerequisite
for reading the canonical evidence/soak inventories. On a host without
`avr-gcc`, its successful v0.9.9 verification nevertheless printed multiple
`avr-gcc: command not found` diagnostics before reporting `QUALIFIED`. The noise
comes from unconditional parse-time compiler probes in `Makefile:527-537`, even
though the requested `print-RELEASE_*` values do not depend on AVR headers or
architecture.

The result is correct, but a metadata-only verifier should not emit apparent
tool failures on a documented tool-independent path. Such noise makes real
warnings easier to miss and complicates automation that treats stderr as a
failure signal.

### Recommended direction

Make compiler discovery lazy or goal-specific, or invoke the canonical metadata
query with an explicit silent compiler placeholder after proving the queried
variables are independent. Do not weaken release-set derivation or let ambient
Make variables redefine the canonical inventory.

### Acceptance criteria

1. Qualification verification passes with only its documented host tools.
2. The successful command emits no compiler-not-found diagnostics.
3. Missing/malformed canonical release inventory still fails closed.
4. Existing ambient-Make isolation tests continue to pass.
