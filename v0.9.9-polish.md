## P1 - Bind release flashing to signed release bytes

**Status:** DONE `97cc3d3`
**Priority:** HIGH
**Scope:** `release/README.md`, `scripts/release-documentation.sh`, `Makefile`,
programming regressions

### Finding

The published PIC12F675 release procedure checks that `HEAD` equals the selected
tag and that the worktree is clean only before the read-only baseline capture
(`release/README.md:327-346`). `pic12f675-program` later rebuilds from the live
tree (`Makefile:6861-6875`), checks calibration and CONFIG, and binds every
subsequent operation to an internally consistent private snapshot
(`Makefile:6893-6918`, `Makefile:6960-6965`). It never proves that the snapshot's
digest is the digest listed for that variant in the signed release
`SHA256SUMS`.

The current transaction is therefore strongly bound to *some fresh build*, but
not necessarily to the released bytes. A source change after the initial check,
an unintended `PIC_CC`/`PIC_DFP` selection, or compiler output that differs from
the qualified release can be programmed while all current transaction checks
report PASS. That contradicts the release provenance promise even when the
resulting firmware is otherwise valid.

### Recommended direction

Create an explicit release-flashing path that knows the selected release tag and
variant. Before hardware is reachable, verify the pinned detached signature,
read the selected image digest from that release's `SHA256SUMS`, and require the
private fresh-build snapshot to match it exactly. Keep the existing
snapshot-immunity checks; signed-release binding is an additional outer
contract, not a replacement.

Recheck the tag/source identity immediately before the private build, or build
from an immutable committed-source view. Account deliberately for the baseline
and result paths created by the published transaction rather than weakening the
clean-tree check globally.

If development/bench programming must remain possible for unreleased source,
make that a distinct, explicit mode or goal. It must not be possible to mistake
an unqualified development build for release flashing.

### Acceptance criteria

1. The correct tagged source and pinned toolchain produce a snapshot whose hash
   matches the signed release record and may reach the fake writer.
2. A tracked source mutation between preflight and program is rejected before
   writer invocation.
3. A compiler that emits a valid but byte-different image is rejected before
   writer invocation.
4. A mismatched release tag, variant, checksum entry, checksum signature, or
   release image set is rejected before writer invocation.
5. The writer still receives exactly the private read-only snapshot checked by
   calibration, CONFIG, and digest gates.
6. Release instructions generated into future manifests exercise the same path
   as the regression tests.

### Resolution

Added `pic12f675-release-program` as a distinct signed-release path while keeping
`pic12f675-program` explicitly available for development and bench builds. The
release path requires an exact clean annotated-tag checkout, verifies the pinned
tag and detached checksum signatures, validates the complete canonical release
image set, and requires the private selected snapshot to match its signed digest
before any hardware command. Baseline, result, and transient paths must remain
outside the worktree so the source checks stay exact.

The fake-programmer regression now covers matching signed bytes, tracked-source
mutation, valid byte drift, tag/signature failures, worktree-local evidence, and
the exact checked snapshot reaching the writer. Release-image regressions cover
variant, checksum-entry, annotated-tag identity, and complete-set failures. The
generated future-manifest transaction invokes the same release target. The
immutable `v0.9.9` tag predates this new target; the protection applies to release
tags that contain it.

## P2 - Make the programming CONFIG gate immutable

**Status:** DONE `a9558cf`
**Priority:** HIGH
**Scope:** `Makefile`, `test/pic/test_config_pic12f675.c`,
`test/pic/test_config_pic_core.h`, `test/test_pic_build.sh`

### Finding

The programming target depends on `test/pic/test_config_pic12f675`, an ignored
generated executable (`test/.gitignore:10-11`). Its file rule has no forced
rebuild and does not encode compiler identity in freshness
(`Makefile:5961-5962`). The programming recipe then accepts that executable on
exit status alone (`Makefile:6704-6706`, `Makefile:6911`).

A newer stale executable, or a zero-exit no-op placed at the ignored path, is
invisible to the published clean-tree check and can silently remove the only
pre-write design-intent check for FOSC, WDTE, PWRTE, MCLRE, BOREN, CP, CPD, and
BG. The calibration checker avoids this class by requiring an exact success
record; the CONFIG checker does not. Current fake-tool tests exercise a bad
CONFIG with a known-good checker and no-op/near-match calibration checkers, but
do not substitute a no-op CONFIG checker.

### Recommended direction

Do not consume a repository-adjacent ignored executable in the hardware path.
Compile the CONFIG checker unconditionally into the private programming
directory, or move the exact PIC12F675 CONFIG policy into an immutable tracked
oracle already used by the transaction. Require an exact image-bound success
record rather than exit status zero.

P1's signed-release digest check will independently protect release flashing,
but P2 remains necessary for development/bench programming and as defense in
depth against generating a dangerous image.

### Acceptance criteria

1. A pre-existing ignored `test/pic/test_config_pic12f675` cannot influence the
   programming transaction.
2. A zero-exit/no-output CONFIG checker cannot make the writer reachable.
3. A near-match or wrong-image success record cannot make the writer reachable.
4. Every safety-relevant CONFIG field and the exact expected word are checked
   against the private snapshot passed to the writer.
5. Bad FOSC, WDTE, MCLRE, BOREN, or BG fixtures fail before any hardware command.

### Resolution

Removed the ignored repository-adjacent CONFIG executable from both programming
targets. Each transaction now compiles the tracked PIC12F675 adapter and shared
policy into its private directory, verifies the executable's type and digest,
and requires one exact record binding `PIC12F675`, the private snapshot path, and
the expected `0x31CC` word before hardware is reachable. The normal all-image
CONFIG target remains unchanged.

The programming regression leaves a newer ignored executable at the old path and
proves it is never run. It also rejects private checker builds that produce no
output, a near-match record, or a record for the wrong image, and independently
rejects unsafe FOSC, WDTE, MCLRE, BOREN, and BG words plus whole-word-only drift
before any fake hardware command. The PIC12F675 lane now contains 103 checks.

## F1 - Correct energized relay coils in place, per tick (mirror PIC10F320)

**Status:** IMPLEMENTED 2026-08-17 (firmware applied by owner; tests, mutation inventory, and doc landed and GREEN, full mutation suite 123/0; only the final full release qualification remains -- see Implementation status)
**Priority:** MEDIUM
**Scope:** `src/bypass_hw_iface.h`; the three shared output drivers; the four
modular relay-capable shells (`bypass_mcu_avr_classic.c`, `bypass_mcu_avr_xt.c`,
`bypass_mcu_pic10f322.c`, `bypass_mcu_pic12f675.c`); the gpsim / yasimavr / simavr
fault harnesses; mutation accounting
**Existing durable TODO:** `TODO.md` `T25-relay-fault-abort`
**Decision:** 2026-08-17 -- correct-in-place model, scope (b) (all relay-capable
shells)

### Finding

Every modular shell can detect an energized relay coil that should be idle (the
per-tick sanity gate, e.g. `src/bypass_mcu_pic12f675.c:571-580`), but its only
response is `hw_force_wdt_reset()`, which disables interrupts and spins
(`src/bypass_mcu_pic12f675.c:307-316`). A coil intended for a 12 ms pulse can
therefore stay energized for a full watchdog period -- roughly 160-480 ms on the
PIC12F675 -- before the reset clears it. The current PIC fault tests inject the
coil bits (`test/pic/test_fault_pic12f675.cc:45-56`) but assert only that a reset
eventually occurs (`test/pic/test_fault_pic_core.h:479-500`).

PIC10F320 already solves exactly this, differently: its relay variant re-asserts
`set_relay_coils_low()` at the TOP of every main-loop iteration
(`src/bypass_mcu_pic10f320.c:617`, guarded `#if defined(OUTPUT_TQ2_RELAY)`), so a
coil-bit upset is corrected within one tick and never reaches a reset. The shared
fault harness already tests that path (`inject_relay_correction_case`,
`test/pic/test_fault_pic_core.h:333`; its pass condition requires
`reset_delta == 0`).

### Decision and rationale

Adopt PIC10F320's correct-in-place model on the four modular relay-capable shells
(PIC10F320 already has it). Reasoning:

- The forced de-energize is a pure no-op on the nominal path -- every actuation
  already ends in `set_relay_coils_low()`, and nothing drives a coil high between
  actuations. It is load-bearing only once an upset has set a coil bit, so the
  only real question is how to respond to that upset.
- Re-asserting the coil low BEFORE the sanity gate makes the response degrade on
  its own. A transient upset (a writable shadow/port bit) is corrected within one
  ~1 ms tick with no reset and no audio dropout. A persistent fault (the pin will
  not follow, direction skewed, a peripheral seized the pin) survives the
  re-assert and is caught by the same tick's sanity gate, which still resets. On
  the shadow-based PIC12F675 gate the persistent case is deterministic -- it
  checks port-follows-shadow -- not merely likely.
- The re-assert cannot spuriously actuate the latch: it repeats every ~1 ms and
  beats the relay's ~4 ms actuation time.
- This unifies both PIC relay shells and brings the AVR relay shells into the
  same model (scope (b)).

This supersedes the earlier "de-energize, then still reset exactly once"
direction. A transient coil upset no longer forces a reset, so coil upsets become
SILENT in the transient case (no reset, no count). That is acceptable -- and in
fact the intended minimum-disruption behavior -- on parts with no telemetry.

### Firmware change (owner-authored)

The interface op and driver bodies are shared, so scope (b) is one shared op plus
one loop-top call per shell. Names are the owner's to finalize;
`hw_outputs_reassert_safe()` is used below.

1. `src/bypass_hw_iface.h` -- declare the op:

       // Re-assert the safe idle level of any output whose safe level is
       // independent of the logical effect state, without changing that state.
       // Called once per serviced tick at the top of the main loop, before the
       // sanity gate, so an upset that energizes such an output is corrected
       // within one tick instead of forcing a watchdog reset.
       void hw_outputs_reassert_safe(void);

2. `src/bypass_output_tq2_l2_5v_relay.c` -- the existing coil safe-state write:

       void hw_outputs_reassert_safe(void) { set_relay_coils_low(); }

3. `src/bypass_output_cd4053_simple.c` and `bypass_output_cd4053_with_mute.c` --
   explicit no-op (CD4053 controls track the effect state; a control-line upset
   has no fixed safe level and stays on the sanity-gate reset path):

       void hw_outputs_reassert_safe(void) { /* no effect-state-independent
                                                 output to re-assert */ }

4. Call it at the top of each modular shell's serviced iteration, BEFORE the
   sanity gate:
   - `bypass_mcu_pic10f322.c`, `bypass_mcu_pic12f675.c`: immediately after
     `hw_wait_for_tick();`.
   - `bypass_mcu_avr_classic.c`, `bypass_mcu_avr_xt.c`: as the first statement in
     the `while (1)` / `for (;;)` body, before the sanity `if`.
   The call is unconditional; the linked driver decides whether it does anything,
   so no shell gains a per-variant `#if`. PIC10F320 stays as-is -- its inline
   re-assert is the reference this brings to the others.

### Test work (mine, after the firmware lands and builds)

- gpsim (`test/pic/test_fault_pic_core.h` + the 322/675 adapters): the relay
  variant's coil injections move from expect-reset to the
  `inject_relay_correction_case` path (corrected within one iteration,
  `reset_delta == 0`). This is variant-split -- the same pins are CD4053 control
  lines in the cd4053 variants and must still reset. Mirror the PIC10F320 relay
  vs. cd4053 adapter split.
- yasimavr (`test/avr/test_fault_attiny202.py` + oracle) and simavr
  (`test/avr/test_sim.c`): apply the same relay-variant coil-correction split.
- LED, spare, SFR, direction, footswitch-pull-up, and context injections are
  unchanged (still expect reset) on every variant.
- Mutation accounting: the loop-top call and the coil-clear in the op add mutants
  (delete the call; delete `set_relay_coils_low()`); both must be behaviorally
  killed by the corrected-without-reset assertion. Update the expected counts.

### Acceptance criteria (revised)

1. A one-coil or both-coil upset on the relay variant is corrected -- both
   physical coil outputs observed low within one serviced iteration -- with NO
   reset, on every relay-capable shell.
2. A coil fault the re-assert cannot fix (pin will not follow / direction skew)
   still forces exactly one watchdog reset, and startup returns to BYPASS.
3. LED, spare-output, SFR, direction, footswitch-pull-up, and context injections
   still reset on every variant (correct-in-place is coil-only).
4. Deleting the loop-top re-assert call, or the coil-clear inside the op, is
   killed behaviorally by the correction assertion.
5. CD4053 variants are byte-unchanged in steady state and keep their existing
   reset-on-upset behavior (the op is a no-op there).
6. Normal relay pulse width and sequencing remain byte-/behavior-qualified after
   the source change.

## F2 - Detect in-range debounce-context corruption

**Status:** IMPLEMENTED 2026-08-18 (firmware applied by owner; pure-core fold, four shells, host/CBMC proofs + MISRA D-5, four-simulator in-range fault injection, and mutation accounting landed and GREEN, full mutation suite 129/0; flash/RAM/stack/MISRA/qualification budgets re-verified -- see Implementation status)
**Priority:** MEDIUM
**Scope:** MCU shells, host/target fault injection, formal/model checks
**Existing durable TODO:** `TODO.md` `T3-ctx-complement`
**Full spec:** `docs/context_seu_detection.md`

### Decision (2026-08-17)

- **Representation:** complemented XOR-fold — one shadow byte
  `= ~(program_state ^ effect_state ^ debounce_counter)`, verified once per tick
  immediately before that tick's integrate. Equivalent single-SEU detection to a
  per-member complement, at one byte / one check.
- **Location:** the fold math is a pure by-value function
  `debounce_ctx_check_word()` in `bypass_pure.c` (host/CBMC-testable single
  source of truth). The shadow's storage, the reset, and the AVR ISR/main
  atomicity stay in the shells (stateless pure core cannot own them).
- **Recovery:** `hw_force_wdt_reset()` — reset, not restore (neither value nor
  shadow is known-good on mismatch).
- **Target set:** enable via a compile-time opt-in `BYPASS_CTX_CHECK` on
  **PIC12F675, PIC10F322, AVR classic, AVR-XT**. **PIC10F320 is excluded** — it
  does not link the pure core and even a one-byte fold overflows its 256-word
  flash; its range-only gate stays, documented and tested as a capacity limit.
- **Flash (measured):** +31 words on the PICs. PIC10F322 relay lands at 507/512
  (**5 words free**) — accepted; the owner must rebuild 322 on landing to confirm
  it stays within budget. PIC12F675 and both AVR parts have comfortable room.
- **AVR note:** because the integrator lives in the timer ISR, the check runs at
  the top of the ISR (before integrate) and sets a fault flag main consumes;
  main's apply + shadow re-derivation is wrapped in one `ATOMIC_BLOCK`.

The full per-shell wiring, the pure-core addition, the measured budget table, the
320-exclusion rationale, and the test/mutation plan are in
`docs/context_seu_detection.md`. On landing, record the decided target set and
effort in `TODO.md` `T3-ctx-complement` (closes F3 acceptance criterion 1 for F2).

### Finding

PIC12F675 rejects only context values above their legal ranges
(`src/bypass_mcu_pic12f675.c:571-578`). A single-bit flip can remain in range and
change behavior without tripping any guard. For example, an idle
`debounce_counter` can flip from 0 to 16; a released sample reduces it to 15
(`src/bypass_pure.c:24-29`), after which `debounce_step()` treats it as a
debounced press and toggles (`src/bypass_pure.c:46-63`). The resulting output
matches the new logical state, so the settled-output check does not catch it on
the next tick.

Target fault tests currently inject out-of-range values such as `0xFF`
(`test/pic/test_fault_pic_core.h:612-617`). They prove range-check recovery but
not the in-range SEU case in the project's threat model.

### Recommended direction

Evaluate complemented or otherwise redundant shell-owned storage for context
members, with every update and every tick checked consistently. Preserve the
pure core and account explicitly for AVR ISR/main ownership. If resource limits
force per-target differences, document and test those differences rather than
silently weakening one target.

The repository owner must make the firmware source edit.

### Acceptance criteria

1. Representative in-range single-bit flips of `program_state`, `effect_state`,
   and `debounce_counter` force recovery before an unintended output transition.
2. Every legitimate context update maintains the redundant representation.
3. AVR ISR/main interleavings cannot produce a false mismatch.
4. Mutation tests kill a missing update and a weakened comparison.
5. Flash, RAM, stack, MISRA, and target qualification remain within each MCU's
   reviewed budgets.

## P3 - Finalize interrupted programming transactions

**Status:** DONE `7bdb71d`
**Priority:** MEDIUM
**Scope:** `Makefile`, `test/pic/pic12f675_trim_evidence.py`, programming tests,
README/release instructions

### Finding

A handled signal exits through programming cleanup immediately
(`Makefile:6829-6847`). If it arrives during or after the writer, the mandatory
post-read and `result.json` creation are skipped. The regression explicitly
expects a retained `reservation.json` and writer log but no final result
(`test/test_pic_build.sh:2050-2065`). Other post-write infrastructure failures
can likewise leave only a PENDING reservation.

The reservation is useful forensic evidence, but the project provides no
read-only recovery/finalization command. Retrying with the same result path is
rejected, and starting a new baseline or write before resolving the existing
transaction risks losing the only reliable account of the device state.

### Recommended direction

Add a recovery/finalization goal that consumes the existing reservation,
performs no write, reads the currently attached device, and publishes a durable
PASS/FAIL resolution bound to the reserved baseline, image, reader, and writer
identity. Where practical, defer handled signals until a best-effort post-read
and FAIL record complete; power loss and `SIGKILL` will still require the
explicit recovery path.

Document physical-custody requirements and prohibit another write, reflash, or
new baseline until the PENDING transaction has been resolved.

### Acceptance criteria

1. A signal after simulated write consumption leaves a PENDING transaction that
   can be finalized without another write.
2. Recovery performs only version/read operations and never invokes writer
   arguments.
3. Matching post-read state produces a resolved record; trim, CONFIG, identity,
   or programmed-byte mismatch produces a durable FAIL record.
4. Reusing a reservation with a different baseline, image, part, variant,
   reader, or writer is rejected.
5. Re-running finalization cannot replace or contradict an existing final
   result.
6. User documentation gives an explicit safe response to PENDING evidence.

### Resolution

Added `pic12f675-finalize` as a read-only resolution path for retained PENDING
transactions. Before device access it validates the baseline, part, variant,
reader and writer executable identities, reservation, and a separately retained
programming image. It then verifies the exact reader version before issuing one
full-device read; writer arguments are never invoked. Matching state publishes a
recovery PASS, while trim, CONFIG, device-identity, malformed-read, or programmed-
byte mismatches publish an exclusive durable FAIL.

Recovery attempts use disposable private subdirectories, so handled signals and
abandoned SIGKILL/power-loss attempts can be retried without replacing forensic
evidence. Terminal results are schema- and digest-validated, replay the safety
oracle, and are sealed read-only; a complete result cannot be replaced or
contradicted. Documentation now requires physical custody of the same device and
prohibits another write, baseline, or result-path reuse until PENDING evidence is
resolved. The PIC12F675 lane now contains 121 checks.

## T3 - Keep metadata-only verification tool-independent

**Status:** DONE 2026-08-19
**Priority:** LOW
**Scope:** `scripts/verify-release-qualification.sh`, Makefile introspection,
release-verifier tests

### Finding

`verify-release-qualification.sh` documents `make` as its only tool prerequisite
for reading the canonical evidence/soak inventories. On a host without
`avr-gcc`, its successful v0.9.9 verification nevertheless printed multiple
`avr-gcc: command not found` diagnostics before reporting `QUALIFIED`. The noise
comes from unconditional parse-time compiler probes in `Makefile:527-537`, even
though the requested `print-RELEASE_SOAK_NAMES` and
`print-RELEASE_EVIDENCE_FILES` values do not depend on AVR headers or architecture.

The result is correct, but a metadata-only verifier should not emit apparent
tool failures on a documented tool-independent path. Such noise makes real
warnings easier to miss and complicates automation that treats stderr as a
failure signal.

### Recommended direction

Make compiler discovery lazy or goal-specific, or invoke the canonical metadata
query with an explicit silent compiler placeholder after proving the queried
variables are independent. Do not weaken release-set derivation or let ambient
Make variables redefine the canonical inventory.

### Acceptance criteria

1. Qualification verification passes with only its documented host tools.
2. The successful command emits no compiler-not-found diagnostics.
3. Missing/malformed canonical release inventory still fails closed.
4. Existing ambient-Make isolation tests continue to pass.

### Resolution

Took the finding's second option -- an explicit silent compiler placeholder --
as the smallest change that closes the stated failure mode.
`scripts/verify-release-qualification.sh` now passes `CC=:` on both metadata
`make` invocations (`print-RELEASE_SOAK_NAMES`, `print-RELEASE_EVIDENCE_FILES`).
The noise came from three unconditional parse-time probes -- `AVR_IO_HEADER`,
`AVR_GCC_INCLUDE`, `AVR_ARCH` -- that shell out to `$(CC)` (default `avr-gcc`)
to locate avr-libc headers for the static analyzers; they run on every `make`
invocation, so a metadata-only query printed `avr-gcc: command not found` three
times on a host without the AVR toolchain. (The cited `Makefile:527-537` had
since drifted to lines 572/581/582.)

The substitution is provably safe: `RELEASE_SOAK_NAMES` and
`RELEASE_EVIDENCE_FILES` are `override :=` literal inventories with no compiler
dependence, so `:` (the shell null utility) satisfies the probes silently and
the query output is byte-identical. It cannot weaken the canonical set --
`override` ignores command-line assignments and `CC` is not an inventory
variable -- which is also why the placeholder had to be a command-line
assignment: the Makefile's `CC = avr-gcc` overrides the environment, so only
`make CC=:` takes effect. The Makefile-side alternative (lazy/goal-specific
discovery) was rejected as larger and riskier: `AVR_LIBC_INCLUDE`'s parse-time
`ifeq`/`wildcard` fallback forces `AVR_IO_HEADER` immediately, so the probes
cannot be cleanly deferred without reworking the analyzer include paths.

A behavioral regression was added to `test/test_release_qualification.sh`: it
shadows `avr-gcc` on `PATH` with a tripwire that fails loudly if invoked and
asserts a valid qualification still passes with no compiler diagnostics on
stderr. It reproduces the real trigger on any host (the tripwire fires three
times without the fix, matching the three probes) and is stronger than a
string check -- it proves the compiler is never invoked. Verified: the verifier
gate is green (48 checks, up one), the metadata query is silent under a
tripwire `PATH` with `CC=:` and noisy without it, and the query output is
unchanged.

## F3 - Scope the F1/F2 fault-handler hardening as a cross-shell campaign

**Status:** DONE 2026-08-18 (scope decided and executed by F1/F2; doc-only closure -- see Resolution)
**Priority:** MEDIUM
**Scope:** all modular MCU shells, per-target fault/mutation tests
**Refines:** F1, F2
**Update (2026-08-17):** F1's model and scope are now decided (see F1 --
correct-in-place, scope (b)). F3's F1-specific text below is superseded by that
decision; F3 now carries only the F2 (context-hardening) scope and rationale.

### Finding

F1 and F2 are written and effort-sized as PIC12F675 items, but both defects are
cross-shell. `hw_force_wdt_reset()` has the same spin-only shape in every
modular shell (F1), and range-only context guarding with no in-range SEU
detection is the shared main-loop pattern (F2). Both items' own acceptance
criteria already span every shell and both ISR/main ownership models, yet the
durable `TODO.md` sizing (`T25-relay-fault-abort`, `T3-ctx-complement`) reads as
a single-part edit. The real surface is every shell x output variant of
owner-authored firmware plus per-target mutation kills.

Two design constraints belong with that scope decision:

- **F2 is bounded to `debounce_counter` for a reason.** The range guard is the
  *sole* guard only for that member. A corrupt `program_state` (any value other
  than 0/1, including a signed-negative flip the `> RELEASE_DEBOUNCE_WAIT` check
  would miss) is caught by the `default:` fault arm of `debounce_step()`
  (`src/bypass_pure.c`), and a corrupt `effect_state` is caught by the
  fail-closed `else` arm of every `hw_is_sanity_check_failed()` variant. The
  shell's other single-byte SRAM values (`osccal_snapshot_`, `gpio_shadow_`) are
  unprotected too, but a flip in either diverges from the port/expected mask and
  trips a reset in the fail-safe direction. Redundant-storage work must cover
  `debounce_counter` (and any equivalently exposed member) and must NOT extend
  to the fail-safe single-byte guards.
- **F1's coil-clear (SUPERSEDED by the F1 decision).** This originally argued the
  coil-clear "belongs in the fault-abort path only, never in the normal path."
  The F1 decision does the opposite on purpose: an idempotent coil re-assert runs
  in the NORMAL path every tick (mirroring PIC10F320). It is a no-op nominally,
  corrects a transient upset before the sanity gate with no reset, and leaves a
  persistent coil fault to the same-tick reset. See the F1 item.

### Recommended direction

Make the target set explicit for F1 and F2: either scope both to PIC12F675 and
record the other shells as knowingly deferred, or re-plan as a cross-target
campaign with a revised estimate. Carry the F2 constraint above into the firmware design so the redundancy work
does not creep to the fail-safe single-byte guards. (The F1 constraint is
superseded -- F1 is resolved by a normal-path per-tick coil re-assert; see F1.)

### Acceptance criteria

1. F1 and F2 each state their target set (single part vs. all shells) with a
   matching effort estimate in `TODO.md`.
2. If cross-shell, per-shell fault and mutation coverage is enumerated for AVR
   classic, AVR-XT, PIC10F320, PIC10F322, and PIC12F675.
3. The F2 redundancy design covers `debounce_counter` and equivalently exposed
   members only, with a written rationale for excluding the fail-safe single-byte
   guards.
4. (Superseded -- see F1.) F1 is resolved by a normal-path per-tick coil
   re-assert; its acceptance criteria live in the F1 item.

### Resolution

F3 asked for an explicit, cross-shell target-set decision for the F1/F2
fault-handler hardening *before* either was implemented as a single-part edit.
Both F1 and F2 have since landed as deliberate cross-shell work, so the scoping
decision F3 called for has been made and executed rather than left implicit.

- **Criterion 1 (target set + effort in `TODO.md`).** Satisfied by removal, not
  annotation, per `TODO.md`'s "completed work is removed" convention. F2's
  `T3-ctx-complement` anchor was removed on completion; F1's `T25-relay-fault-abort`
  anchor is removed here. `T25-relay-fault-abort` had become actively misleading:
  it described the *rejected* abort-path model ("clears both coil drivers before
  entering the reset wait") and even instructed to keep that "separate from
  PIC10F320 idle re-drive" -- the opposite of what F1 shipped (it brought the
  PIC10F320 per-tick idle re-drive model to the other shells). The decided target
  sets and effort now live in the F1/F2 *Implementation status* subsections and,
  durably, in `docs/relay_coil_fault_correction.md` (F1) and
  `docs/context_seu_detection.md` (F2), with `CHANGELOG.md` and Git history as the
  permanent record.
- **Criterion 2 (per-shell fault and mutation coverage enumerated).** Enumerated
  for all five parts in the F1 and F2 *Implementation status* subsections: F1 --
  PIC12F675 gpsim relay 45/0 + cd4053 37/0, PIC10F322 gpsim relay 26/0 + cd4053
  25/0, AVR classic simavr relay 72/0 + cd4053 66/0, ATtiny202 yasimavr relay
  22/22 + cd4053 22/22, plus mutation lanes CORE/XT/PIC_TARGET/PIC12F675; F2 --
  in-range injection on all four simulators plus mutation coverage across every
  detection surface, full suite 129/0, with PIC10F320 statically asserted to carry
  no F2 machinery.
- **Criterion 3 (F2 covers `debounce_counter` and equivalently exposed members
  only).** Satisfied and recorded durably: the F2 fold is exactly the three
  context members (`program_state ^ effect_state ^ debounce_counter`) and
  deliberately excludes the fail-safe single-byte guards (`osccal_snapshot_`,
  `gpio_shadow_`), whose corruption already diverges from the port/expected mask
  and resets in the fail-safe direction. The rationale lives in
  `docs/context_seu_detection.md`.
- **Criterion 4.** Superseded by the F1 decision, as noted above.

No firmware or test changes: F3 is closed by the F1/F2 implementations already on
the branch plus this scope-and-record reconciliation. The only fault-hardening
work knowingly deferred beyond this branch is the broader formal/output-sequencing
campaign tracked under the durable `TODO.md` `T25-` entries (e.g.
`T25-output-formal`), which is out of F3's scope.
