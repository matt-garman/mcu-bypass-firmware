= Toolchain Reference

This file documents the exact toolchain versions used to build and
test the bypass firmware.  It serves the same purpose as a Python
requirements.txt: a human-readable record of what the project was
validated against, so a new developer (or CI system) can reproduce
the exact environment.

This is a requirements and historical-environment record, not proof that every
gate ran at the current tip. Measured results and qualification status for any
released version are retained under `release/<version>/`, which identifies the
qualified source commit.

Classic AVR firmware targets rebuild whenever they are requested, ensuring the
current compiler, flags, and source tree are always consumed.  If you update a
tool, re-run `make clean && make test` before relying on its output.

== Development platform

  OS:           Linux 6.12.33 (TrueNAS production kernel), x86_64
  Distribution: Ubuntu 24.04 (Noble) base packages

  flock:        util-linux (required). Complete Make and direct release-script
                invocations use one worktree-local advisory lock because build,
                test, coverage, and simulator artifacts are intentionally shared.
  timeout:      GNU coreutils (required). Mutation and simulator checks use
                bounded wall-clock execution.
  setsid:       util-linux (required). Each bounded mutation checker owns an
                isolated process session for descendant cleanup.
  ps:           procps (required). Mutation interruption cleanup enumerates the
                process groups in each owned checker session.

  Git:          git (required). Release-history/signature tests construct and
                inspect temporary repositories; ci-local also requires a real
                worktree before reproducing CI.
  GnuPG:        gnupg / `gpg` (required). Release-history regressions generate
                ephemeral signing keys and verify detached/tag signatures.
  PyYAML:       python3-yaml (required for strict runs). Workflow syntax and
                job-structure validation imports `yaml`; `STRICT_TOOLS=1` turns
                an absent module into a hard failure.

== PIC toolchain (PIC10F322, PIC10F320 and PIC12F675, optional second toolchain)

ONE XC8 + device-pack installation serves ALL THREE PIC parts. They are kept on
two Makefile variable pairs (`PIC_CC`/`PIC_DFP` for the 10F322 and the 12F675,
`PIC10F320_CC`/`PIC10F320_DFP` for the 10F320) so the 320 can be re-pinned to a
different compiler or pack without silently moving the other two; by default the
320's variables track the 322's. The release manifest probes and records both
selected compiler paths and versions independently, even when they resolve to
the same installation. The PIC12F675 is release-supported from `v0.9.9` and
shares the 322's `PIC_CC`/`PIC_DFP` pair; the release manifest records its
images alongside the other PICs, and it is gated in CI on the same installation.

The PIC10F322 port (`make pic10f322`, `make pic10f322-test`,
`make pic10f322-test-target-variants`) is a SEPARATE, optional toolchain, entirely
independent of the AVR build above and deliberately NOT part of `make test` (the
AVR pre-hardware gate).  Individual PIC targets skip cleanly when their tools
are absent, so the AVR workflow is unaffected if these are not installed.  CI
and release use `STRICT_TOOLS=1` and the fail-closed `pic10f322-test-target-variants`
aggregate so missing PIC tooling cannot produce a false green release gate.

=== The free tier caps the optimizer, and that is a design input

XC8 is used unlicensed.  The free tier runs the portable, IR-level
optimizations -- inlining, dead-code elimination, GVN -- but gates the
PIC-specific machine-level passes behind a PRO license, so `-Os` is accepted
and then downgraded with advisory 2051: *"the current license does not permit
the selected optimization level, using optimization level 2"*. Exact image size
is source-dependent and belongs in retained release evidence. The historical
fit experiment that selected PIC10F320's self-contained architecture is bound
to its source commit, XC8 version and device pack in "PIC10F320: the constrained
target" in DESIGN_DOCUMENTATION.adoc.

This is worth stating because the obvious workarounds do not exist.  The passes
that would shrink 8-bit PIC code -- compiled-stack overlay, bank and page
minimization, procedural abstraction -- are architecture-specific back-end work
in Microchip's Optimizing Code Generator, not portable IR passes any optimizer
can run.  Upstream LLVM has no 8-bit PIC target at all, so XC8's clang front end
cannot emit code for these parts without that back end.  Compiled-stack overlay
is in addition a whole-program decision, so there is no hand-off point where a
foreign tool could contribute optimized objects.  SDCC's `pic14` port does
target these parts, but without those optimizations, with experimental
enhanced-mid-range support, and in a separate ABI, runtime and CONFIG world
that would require a forked firmware shell.

The consequence that matters is recorded in "PIC10F320: the constrained target"
in DESIGN_DOCUMENTATION.adoc: the modular architecture's failure to fit 256
words is measured against this tier, and the remaining levers are a paid
license or hand-written assembly, neither of which this project will take.

  PIC12F675
  programmer:    `pk2cmd` is the only pinned readback dialect. Run
                 `make pic12f675-preflight PIC12F675_TRIM_EVIDENCE=<new-file>`
                 before the first write. Its read-only `-GF<file>` transaction
                 records the exact executable digest/version transcript,
                 target Device ID/revision transcript, complete read-HEX
                 digest, factory `RETLW` word at 0x3FF, CONFIG at 0x2007, and
                 `BG<1:0>`. The output path is exclusive and is never replaced.
                 `make pic12f675-program` requires that baseline plus a new
                 `PIC12F675_BENCH_RESULT` directory path. It repeats the read immediately
                 before writing and requires the complete export, device
                 identity, OSCCAL, CONFIG, and BG to match. A baseline therefore
                 belongs to one device before its first write and must not be
                 reused for a later reflash. The target programs
                 the immutable checked image, reads again, compares every image
                 byte (masking only factory BG bits), and retains the raw
                 writer/readback transcripts and before/after fields. The
                 directory is exclusively reserved with `reservation.json`
                 before the write, so an interruption cannot erase all account
                 of the transaction; `result.json` is the final verdict. A failed
                 write, failed post-read, or changed trim produces retained
                 FAIL evidence and a failing Make target.

                 Transient full-device reads and the private programming build
                 use `TMPDIR` when set, otherwise `XDG_RUNTIME_DIR`, otherwise
                 `HOME`. The selected root must already exist, be owned by the
                 current user, grant no group/other access, and have no
                 ancestors except those owned by the current user or root; those
                 ancestors must not be group/other-writable. Shared `/tmp` and
                 `/var/tmp` roots are rejected. Its path may contain letters,
                 digits, spaces, `/`, `.`, `_`, and `-`. The transient
                 directories are created mode 0700 and removed on success,
                 failure, or a handled signal. Only the explicitly requested
                 baseline and result paths are retained.

                 ipecmd remains a software-tested write dialect for this Make
                 route. The current target would require pk2cmd reads immediately
                 before and after the IPE write; no safe dual-programmer
                 attachment or handoff is hardware-validated, so this route
                 offers no operator ipecmd procedure and claims no ipecmd read
                 argv. The downloaded-release helper is the separate route that
                 does publish one: the helper's `ipecmd` route is published and
                 software-tested, but it is not hardware-qualified (see
                 `FLASHING.md`). Neither programmer is
                 installed on this build host, so fake-tool coverage validates
                 command routing and fail-closed evidence handling, not silicon
                 preservation. That silicon preservation and a safe IPE setup are
                 part of the `1.x.y` hardware-validation pass (TODO
                 `T3-pic12f675-bench`), which every part in this repository still
                 awaits.

XC8 / device-pack behaviours relied on (proven against V3.10 + DFP v1.9.189):

  - XC8 V3.10 compiles C99 only (no C11); the firmware's static_assert is shimmed
    to the _Static_assert keyword in src/bypass_static_assert.h.
  - XC8 rejects -fshort-enums, and its enum sizing is TWO-FACED: the clang
    front end (which evaluates sizeof and _Static_assert) sizes enums as int,
    so sizeof(debounce_context_t) is 5 -- but the CODE GENERATOR packs each
    enum to the smallest sufficient type, so _ctx_ actually assembles to
    `ds 3` with fields at byte offsets +0/+1/+2 (verified, including with
    volatile members, i.e. it is systematic layout, not an optimization).
    Consequences: (a) a static_assert CANNOT pin the real layout -- the PIC
    libgpsim tests assert `_ctx_: ds 3` from the generated .s instead, since
    their ctx_ SRAM offsets and the RAM figures in DESIGN_DOCUMENTATION.adoc
    depend on it; (b) never take sizeof of an
    enum-bearing type in PIC-shell code (e.g. memset(&ctx_, 0, sizeof ctx_)
    would write 5 bytes over a 3-byte object).  The atomicity angle is
    harmless either way: the PIC shell is single-threaded (polled tick, no
    ISR-shared state), so the 8-bit atomicity the AVR build gets from
    -fshort-enums is not needed.
  - const-qualified locals are placed in program ROM, so a const local
    initialised from a runtime call is rejected; the PIC shell drops that const.
  - _XTAL_FREQ (for the drivers' __delay_ms) is supplied via -D in the Makefile,
    parallel to the AVR's -DF_CPU.

Device budgets, both gated per variant on every build:

  PIC10F322:  512 words of flash, 64 bytes of RAM   (`make pic10f322`)
  PIC10F320:  256 words of flash, 64 bytes of RAM   (`make pic10f320`)
  PIC12F675: 1024 words of flash, 64 bytes of RAM   (`make pic12f675`)

The PIC12F675 build additionally parses XC8's exact `Data space used` summary,
cross-checks hexadecimal and decimal usage plus the 64-byte capacity, and
enforces an inclusive 48-byte policy limit for every variant. Missing,
duplicate, malformed, inconsistent, or over-limit summaries delete the complete
image matrix. The 16-byte remainder is allocation headroom; XC8's Data-space
total already accounts for statically overlaid automatic storage.

See "Resource Utilization" in DESIGN_DOCUMENTATION.adoc for each part's
capacity, its reviewed ceiling, and the gate that enforces it; the measured
per-variant figures belong to the release record.  The 320's margins are tight
enough to be a design input rather than a footnote: they are why one of the
PIC10F322 shell's defensive checks could not be ported to it; see
"PIC10F320: the constrained target" in DESIGN_DOCUMENTATION.adoc.

Its build output goes to build_pic10f320/ (build and coverage artifacts alike),
kept separate from the 322's build_pic10f322/ and from the shared top-level coverage/.

The final-HEX stack oracle decodes the PIC10F320's classic 35-instruction
mid-range PIC14 ISA directly. `CALL`/`GOTO` use masks `0x2000/0x3800` and
`0x2800/0x3800`; `BTFSC`, `BTFSS`, `DECFSZ`, and `INCFSZ` each fork into
independently tested skip and no-skip outcomes. `RETURN` and the complete classic
`RETLW` alias range (`0x3400..0x37ff`) pop the exact abstract hardware stack;
the complete `MOVLW` alias range (`0x3000..0x33ff`) falls through. Reserved words
fail closed instead of acquiring an opcode from another PIC14 ISA. The model
rejects `RETFIE`, direct PCL writes, data-dependent writes through classic
`INDF`, and any reachable write that could enable GIE because those can introduce
unmodelled successors or asynchronous pushes. Full opcode-mask rationale and
fail-closed fixtures are in `test/pic10f320/return_stack_oracle.py`.

PIC10F320 has a 9-bit architectural PC and 256 implemented physical words.
`CALL`/`GOTO` targets, sequential/skip PCs, pushed return addresses, and popped
successors normalize to `0x000..0x1ff`; only instruction fetch aliases through
the low eight bits to physical words `0x00..0xff`. The per-build check runs inside
`pic10f320`'s existing incomplete-image trap; an oracle, Python, or analysis failure
removes that build output. This does not make an artifact immutable after the
recipe returns. The complete-matrix target and release provenance/reproduction
gates provide later rechecks at their own use points.

                attiny202-test-target with STRICT_TOOLS=1, soak one combination

                vendored bug-fix patches in third_party/yasimavr/patches/.
                Idempotent (stamped on version + sdist SHA + patch-set SHA).
  needs:        python3 + python3-venv + python3-dev and a C++ compiler (it
                compiles yasimavr's C++/SIP extension modules from source,
                ~75 s), plus curl/wget and network access to PyPI.  pip must
                come from python3-venv's own ensurepip: there is no download
                fallback, and a host whose venv comes up without pip is failed

                test/test_fetch_yasimavr.sh).
  install:      sudo apt install python3 python3-venv python3-dev g++ curl
                scripts/fetch_yasimavr.sh
  patches:      two upstream yasimavr bugs (reported upstream) block our
                fuse-locked-WDT firmware and are carried as the vendored patches:
                (0001) the tinyAVR 0-series device builder omits the WDT
                peripheral, so any WDT register access crashes the simulated CPU;
                (0002) ArchXT_WDT maps WINDOW=OFF to a 4-clock window instead of
                0, resetting a correctly-petted WDT ~every pet.  Bug 0002 lives
                in compiled C++, so a patched BUILD is required -- a runtime
                monkeypatch cannot reach it.
  scope:        yasimavr models the ATtiny202 TCB0 tick, the fuse-locked WDT
                (real reset + STATUS.LOCK), RSTCTRL and PORTA (input + output)
                well enough to run the REAL built image.  It treats the shell's
                interrupts-off force-reset spin (cli; for(;;){}) as a terminal
                halt, so it cannot show the watchdog PHYSICALLY completing that
                reset (a hardware guarantee); the fault test asserts the sanity
                gate ENTERING the force-reset path instead, and the watchdog
                liveness reset (out of SLEEP) is observed directly.  The fault
                matrix also corrupts each application pin's PORTA.PINnCTRL.INVEN
                bit, including PA7 with its pull-up preserved, so polarity faults
                cannot pass through latch/direction checks.  Relay cases observe
                modeled PA2/PA3 pin levels at the reset spin and additionally
                cover coil pull-up, one-bit direction and combined
                stale-register states; a low OUT latch alone is not accepted
                as quiescence.  The pure debounce core keeps its full host +
                formal coverage regardless.
                See test/avr/sim_attiny202.py.
  builds on:    the ATtiny_DFP device files (scripts/fetch_attiny_dfp.sh, pinned
                atpack) that `make attiny202` needs to COMPILE the image; those
                are a Microchip download, fetched on demand, not committed.

== Host toolchain (native test harnesses)

  gcc:          13.3.0  (Ubuntu 13.3.0-6ubuntu2~24.04.1)
  clang:        18.1.3  (Ubuntu LLVM 18.1.3, package: clang-18)

  Either compiler works for all test/* host binaries.  The Makefile uses gcc
  by default (HOSTCC ?= gcc); set HOSTCC=clang to override.

  Minimum host gcc version: 10 (any Clang).  Every host gate compiles firmware
  sources with -Werror -Wconversion, and gcc 9 and older report a FALSE
  narrowing there: they fold an explicit (uint8_t) cast away whenever the
  operand provably fits in eight bits -- a narrow bitfield read, or a read
  masked with a small constant -- and then blame the compound assignment that
  writes the folded result back.  The PIC10F322 shell's OR-folded integrity
  checks use exactly that shape, so gcc 9 rejects
  pic10f322-coverage-check-fw over correct firmware.  gcc 10 (2020) fixed the
  diagnostic; measured here, gcc 9.5.0 reports four such errors and gcc 10.5.0
  reports none, on identical sources.  Writing the casts to satisfy gcc 9 costs
  PIC10F322 flash the 512-word cd4053_with_mute variant cannot spare, so the
  floor is enforced instead: `make host-compiler-valid` probes the construct
  itself (test/host_compiler_version.sh) and every aggregate runs it second,
  right after python-version-valid.

  Note this is a floor on the HOST compiler only.  It says nothing about the
  image-defining avr-gcc/XC8 pins below, which are exact-version contracts.

== Static analysis

  clang-tidy:   18.1.3  (from LLVM 18 packages)
  cppcheck:     2.13.0  (Ubuntu package: cppcheck)
  clang --analyze: provided by clang 18 (no separate install)

  All three are wired into `make analyze`; that target's cppcheck/MISRA portion
  runs the ten Classic rows.  The standalone AVR-XT and PIC analyzer targets
  complete a declarative 30-row semantic matrix per mode across distinct
  ATtiny13A/tinyx5/AVR-XT/PIC10F322/PIC10F320/PIC12F675 target models, explicit
  output selectors, and every shipping C translation unit under each materially
  relevant header model.  Warnings are treated as errors.  PIC analysis uses
  C11 parsing as an analyzer accommodation; the image-defining XC8 builds remain
  C99 and are the production-language authority.

== Reproducing the environment (Ubuntu 24.04)

  sudo apt install make util-linux git gnupg python3 python3-yaml \
                   gcc-avr avr-libc simavr libsimavr-dev libelf-dev \
                   gcc clang clang-tidy cppcheck

  Optional analysis tools:
  sudo apt install valgrind lcov gcovr

  Optional PIC10F322 port (`make pic10f322` / `make pic10f322-test` /
  `make pic10f322-test-target-variants`):
  sudo apt install gpsim          # the PIC simulator (apt)
  # For the libgpsim fault/lock-step/target-I/O gates and the soak:
  sudo apt install gpsim-dev libglib2.0-dev g++ pkg-config
  # XC8 V3.10 + the PIC10-12Fxxx_DFP pack are separate Microchip downloads
  # (see the PIC toolchain section above).  Without them, the pic* targets
  # skip cleanly and the AVR `make test` is unaffected.  Release/CI use
  # STRICT_TOOLS=1 plus `make pic10f322-test-target-variants`, where any skip fails.

  Mutation tests may be allowed to skip locally with `MUTATION_ALLOW_SKIP=1`
  (the non-strict default).  Selective partial runs use `PIC`, `ATtiny202`, or
  `PIC,ATtiny202`; an unlisted substrate remains fail-closed. Full-toolchain and
  release runs use `MUTATION_ALLOW_SKIP=0` or `STRICT_TOOLS=1`.

  ATtiny202 (AVR-XT) build + dynamic harness (`make attiny202`,
  `attiny202-sim` / -fault / -lockstep / -soak; run in normal CI, in release
  qualification, and optionally locally):
  sudo apt install python3 python3-venv python3-dev g++ curl binutils-avr
  scripts/fetch_attiny_dfp.sh     # Microchip device files (to build the image)
  scripts/fetch_yasimavr.sh       # patched yasimavr venv (to run it)
  # Both are version-pinned, fetched on demand, and NOT committed.  Without them
  # the attiny202-* targets skip cleanly and `make test` is unaffected (see the
  # yasimavr entry under "Simulator" above) -- EXCEPT under STRICT_TOOLS=1, which
  # release qualification uses to turn every such skip into a hard failure.
  # scripts/make-release.sh asserts both up front and refuses to start without
  # them, so a release can never ship an ATtiny202 image that no simulator saw.

  Before starting the long release pipeline, run `make release-preflight`. It
  executes the release script's real step 0 — selected compilers/tools, both

  version probes — and exits before cleaning, building or staging. It also runs
  short preprocess/link probes for avr-libc, simavr/libelf and both libgpsim C++
  lanes, so installed command names alone are not sufficient. A version is
  optional; `make release-preflight VERSION=vX.Y.Z` also reports local/remote tag
  and output-directory conflicts as warnings.

== Version pinning strategy

Exact versions above were the latest Ubuntu 24.04 LTS packages at the time
of initial commit.  Upgrading minor versions of avr-gcc or avr-libc is
generally safe.  If avr-gcc major version changes, re-verify with
`make test` and inspect the generated assembly for the ISR to confirm
the saturating integrator still compiles to the expected atomic read-
modify-write pattern (no multi-byte intermediates).

For CI reproducibility, prefer Ubuntu 24.04 LTS Docker image:

....
    docker run --rm -v $(pwd):/src ubuntu:24.04 bash -c \
      "apt-get update && \
       apt-get install -y make util-linux gcc-avr avr-libc simavr libsimavr-dev libelf-dev \
                          gcc clang clang-tidy cppcheck cbmc \
                          git gnupg python3 python3-yaml && \
       cd /src && \
       GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=safe.directory GIT_CONFIG_VALUE_0=/src \
         make test STRICT_TOOLS=1"

The image is minimal: `apt-get update` and `make` itself are required, and
`make test` runs the analyzers (clang-tidy, cppcheck), the MISRA addon (needs
`python3`), workflow parser (`python3-yaml`), release history/signature fixtures
(`git` + `gnupg`), and CBMC (`cbmc`) -- omitting any of these makes the
corresponding gate skip or fail. The command pins `STRICT_TOOLS=1` so an optional
strict gate cannot validate nothing. The process-local Git override trusts only
the `/src` bind mount for this invocation; Docker runs as root while the mounted
repository is normally owned by the host user, so modern Git otherwise rejects
it as dubious ownership. It does not write Git configuration. For the
authoritative, tested command set, use `scripts/ci-local.sh` (it mirrors the CI
job order).

== What the release enforces

The sections above are a REQUIREMENTS and historical-environment record, not a
claim that the release job pins the runner image or every tool. That distinction
matters, so here is exactly what a signed release ENFORCES versus what it merely
RECORDS.

Enforced -- a release cannot ship otherwise:

* *Image bytes.* Every published `.hex` is rebuilt on a clean runner and compared
  BYTE-FOR-BYTE against the signed `SHA256SUMS`. This is the final, independent
  gate; it does not depend on trusting any tool-version claim.
* *Image-defining compilers, version-pinned and preflight-enforced.* avr-gcc
  7.3.0 and XC8 V3.10 (PIC10F322 and PIC12F675 share one XC8 selector, PIC_CC;
  PIC10F320 has its own, PIC10F320_CC). `scripts/make-release.sh` HARD FAILS at
  preflight -- before any build or soak -- if any of these three drifts from its
  pin, rather than warning and leaving it to the byte gate.
+
The comparison is EXACT: a whole version token is parsed out of the banner of
the tool each Make variable actually selects, and compared for equality. A
version that merely CONTAINS the pin is drift and is rejected -- avr-gcc 17.3.0
and 7.3.0.1 do not satisfy the 7.3.0 pin, and XC8 V3.100 and V13.10 do not
satisfy the V3.10 pin -- as is a banner carrying no version token at all, or
more than one. Until v0.9.10 these three checks were shell substring patterns,
which accepted the first three of those four drifted versions.
* *Production release identity.* The Makefile pins the complete product identity
  and basename convention as literal `override` text
  (`RELEASE_IDENTITY_PINNED` and the image/soak sets beside it), and both a
  `make release` goal and `scripts/make-release.sh` itself refuse to start if
  the values the run actually selected differ from it -- before any clean,
  build, soak, staging or scratch directory. That covers the image basename,
  the tinyx5 membership, every MCU tag, every die and clock selector, and the
  variant sets, on BOTH channels: a command-line assignment and an inherited
  export, the latter because the per-part tags and die selectors are `?=` and
  the environment wins those without appearing in any command. Build-directory
  and tool-path overrides are unaffected and stay available -- they do not
  change what an artifact IS, and the selected tool is asserted and recorded
  separately. A release-only fail-closed allowlist also rejects source-list,
  compile/link-flag, and validation-control overrides; assignment-bearing
  `MAKEFLAGS`/`GNUMAKEFLAGS`; GNU Make `--eval`; noncanonical/injected makefiles;
  and dollar-bearing values before a selected tool or release recipe runs. The
  canonical and pinned image/soak inventories must contain unique members before
  their complete sets are compared; sorting cannot hide a duplicate. The sole
  live human-readable topology is the bounded current-release declaration in
  `release/README.md`. The separately selectable `PIC12F675_PYTHON` is executable- and
  minimum-version-checked, passed to qualification, and recorded in the signed
  manifest.
* *XC8 + PIC10-12Fxxx_DFP provenance and cache integrity.*
  `scripts/install_pic_toolchain.sh` installs only after both downloads match
  reviewed SHA-256 digests (the XC8 installer and the 1.9.189 atpack), then
  freezes an integrity manifest of the extracted tree.
  `scripts/verify_pic_toolchain_cache.sh` re-checks the RESTORED cache against
  that manifest on every CI restore -- the cache bypasses the SHA-verified
  installer -- and rejects a corrupted, incomplete, or symlinked tree before any
  build or test. The ATtiny_DFP cache is self-verified the same way by
  `scripts/fetch_attiny_dfp.sh`; the patched yasimavr venv is pinned by sdist
  version + SHA + patch-set SHA.

Recorded but deliberately NOT pinned:

* The hosted-runner label (`ubuntu-24.04`) is a MOVING image, and the apt tools
  install without version constraints.
* Analyzer and simulator versions (cppcheck, clang-tidy, CBMC, simavr, gpsim,
  binutils-avr, avr-libc, host gcc, Python) ride whatever that runner ships.
  `scripts/make-release.sh` reads each one THROUGH its Makefile variable and
  records the exact version into the signed provenance MANIFEST, so runner or
  package drift cannot silently change which analyzer/simulator supplied a given
  release's evidence: the version that ran is attested even though it is not
  pinned. Byte-for-byte image reproduction remains the final artifact gate
  regardless.
